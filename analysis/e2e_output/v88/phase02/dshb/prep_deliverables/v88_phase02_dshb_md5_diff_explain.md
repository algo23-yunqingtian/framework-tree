## 2. 根因分析：CRLF行尾符归一化

### 2.1 技术事实

| 文件 | CRLF行尾数 | 文件大小 | 差异量 | 差异原因 |
|------|:---------:|:--------:|:------:|:--------:|
| `dshb_data_supply_engine.py` | **640** | 26,217B | +640B | CRLF=2字节, LF=1字节, 每处+1B |
| `v88_phase02_dshb_data_operation_report.md` | **430** | 18,393B | +430B | 同上 |

**精确吻合**: 文件大小差异（+640B / +430B）与CRLF行尾数量（640 / 430）**完全一一对应**，每个CRLF字符对比LF多1字节。

### 2.2 成因链

```
原始提交 (Linux/macOS)           →  MD5_MANIFEST记录时           →  当前Windows检出
─────────────────────────        ────────────────────────        ─────────────────────
行尾: LF (0x0A)                   MD5 = C62F4E95 (LF版)           git checkout → CRLF (0x0D 0x0A)
                                  MD5 = 0F5D9A52 (LF版)           MD5 = 4E22B6BA (CRLF版)
                                                                         MD5 = 063F1534 (CRLF版)
```

具体时序：
1. **DSHB提交时**: 2份文件使用LF行尾，MD5由`MD5_MANIFEST.md`记录为`C62F4E95`和`0F5D9A52`
2. **CRLF归一化提交 `06e6070`**: 在v85_final_archive路径的CSV和MD5_MANIFEST_cross_review.md上执行了CRLF归一化
3. **Windows检出**: `git checkout`在Windows环境自动将LF转换为CRLF（core.autocrlf=true）
4. **审计时**: HERMEShf在Windows上计算MD5，得到的是CRLF版的哈希值

### 2.3 为什么其余5份文件不受影响

其余5份文件（3个JSON + 1个MD报告 + 1个MD报告）在git checkout时保持LF行尾不变，可能原因：
- 这些文件在git仓库中已设置为`text=auto`或`.gitattributes`未明确指定行尾转换
- 这些文件可能在后续提交中被重新写入为LF行尾（覆盖操作或新建）
- git的CRLF转换策略对不同类型的文件有不同处理

2. 执行`git config core.autocrlf false`后重新计算MD5
3. 使用`git diff --ignore-space-at-eol`验证内容一致性

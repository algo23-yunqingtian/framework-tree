P0-12 门禁当前 FAIL（`cpu_peak_pct=99.4871% > 1.75%`）。已实施两项优化（LRU cache warmup + render pre-caching），总改善仅 0.038%，优化空间已接近天花板。

## 2. 方案一：分片渲染（Sharded Rendering）

### 2.1 方案描述

将 101 张图表的渲染任务拆分为多个分片，每片包含 10-20 张图表，串行渲染各分片，分片间释放 CPU 让出时间片。

### 2.2 评估

| 维度 | 评估 |
|------|------|
| CPU 降幅 | **0%**（分片不减少总计算量，仅改变调度顺序，`process_time/wall_time` 比值不变） |
| 开发成本 | 2 人天（重构渲染调度器 + 分片配置 + 测试） |
| 图表精度 | 无影响 |
| 业务影响 | 渲染总时长可能增加（分片间隔引入空等时间），P99 延迟可能恶化 |
| 风险 | 🟡 中（增加调度复杂度，可能引入超时 bug） |

### 2.3 结论

**不推荐**。分片渲染不改变 `process_time/wall_time` 比值——CPU 密集型任务无论怎么切片，总 CPU 时间不变。唯一效果是拉长 wall_time（引入空等），反而可能让 `cpu_pct` 下降（因为分母增大），但这是**数值游戏不是真优化**。

## 3. 方案二：结果缓存预渲染（Result Cache Pre-rendering）

### 2.1 方案描述

在业务低峰期（如凌晨 02:00-04:00）预渲染所有 101 张图表，将渲染结果缓存到磁盘。业务高峰期直接读取缓存，跳过 render 阶段。

### 3.2 评估

| 维度 | 评估 |
|------|------|
| CPU 降幅 | **~50%**（render 阶段 CPU ≈ 总 CPU 的 49.96%，缓存命中后该部分归零） |
| 开发成本 | 5 人天（缓存序列化/反序列化 + 失效策略 + 预渲染 cron + 缓存一致性校验） |
| 图表精度 | ⚠️ 数据新鲜度降低（缓存内渲染结果基于旧数据，最多延迟 24h） |
| 业务影响 | 高峰期渲染从 ~40s 降至 ~20s（data_load 不受影响）；但凌晨预渲染增加额外 CPU 开销 |
| 风险 | 🟡 中（缓存不一致导致图表显示旧数据，需配合数据更新频率设计失效窗口） |

### 3.3 实施条件

- 缓存命中率须 ≥95% 才有收益（低于此值预渲染成本 > 收益）
- 数据更新频率 ≤24h 的图表才适合预渲染（实时行情类不适用）
- 需新增 `cache_invalidation` 机制，数据更新时触发对应图表缓存失效

### 3.4 结论

**条件推荐**。可降低约 50% CPU（render 阶段），但以牺牲数据新鲜度为代价。适合 Phase04 扩量到 216 指标后考虑。当前 Phase03 阶段不实施——101 图表的数据新鲜度要求参差不齐，贸然缓存可能导致关键图表显示过期数据。

## 4. 方案三：异步任务队列（Async Task Queue）

### 4.1 方案描述

将渲染任务改为异步执行（`asyncio` 或 `celery`），主线程提交任务后不阻塞等待，CPU 在 I/O 等待期间可被其他任务使用。

### 4.2 评估

| 维度 | 评估 |
|------|------|
| CPU 降幅 | **0%**（异步不减少 CPU 计算量，仅在 I/O bound 场景提升吞吐；渲染是 CPU bound，异步无改善） |
| 开发成本 | 8 人天（全链路异步改造 + 事件循环 + 错误处理 + 测试） |
| 图表精度 | 无影响 |
| 业务影响 | 渲染延迟从同步变为异步（用户等待可能增加，取决于队列深度） |
| 风险 | 🔴 高（全链路异步改造触及核心引擎，可能引入竞态条件、死锁、内存泄漏） |

### 4.3 结论

**不推荐**。异步任务队列优化的是 I/O bound 场景的吞吐量，而本场景的瓶颈是 **CPU bound**（data_load + render 两阶段 CPU 密集），异步化不减少 CPU 计算总量。改造风险高、成本大、收益为零。

## 5. 方案四：渲染精度降级（Render Precision Degradation）

### 5.1 方案描述

在 CPU 高峰期降低渲染精度：跳过非关键图表的 fallback 逻辑、减少数据点采样（如从 500 点降采样到 200 点）、跳过统计派生图表。

### 5.2 评估

| 维度 | 评估 |
|------|------|
| CPU 降幅 | **~15-30%**（取决于降级粒度，跳过 50% 图表可降 ~25% render CPU → 总 CPU 降 ~12.5%） |
| 开发成本 | 3 人天（降级策略配置 + 动态切换逻辑 + 恢复机制 + 测试） |
| 图表精度 | ⚠️ **降级图表精度下降**（降采样引入数据失真、跳过图表为空白） |
| 业务影响 | 高峰期部分图表显示不全/精度降低，用户体验下降 |
| 风险 | 🟡 中（需定义降级触发/恢复条件，避免降级后无法恢复） |

### 5.3 实施条件

- 需定义"非关键图表"清单（与业务方确认）
- 降级触发条件：CPU >80% 持续 >60s
- 恢复条件：CPU <50% 持续 >120s
- 降采样不得影响关键定价指标

### 5.4 结论

**条件推荐（仅限极端高峰）**。可降低 12.5-25% 总 CPU，但以牺牲图表完整性为代价。适合作为 Phase04 扩量后的**应急降级策略**，非日常优化手段。当前 Phase03 不实施——101 图表全部有业务价值，降级会影响审计完整性。

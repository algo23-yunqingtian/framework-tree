## 二、测试结果

### 2.1 单Case延迟 (S1)

| 指标 | 值 |
|------|-----|
| 平均延迟 | 0.212 ms/case |
| p50 延迟 | 0.218 ms |
| p95 延迟 | 0.225 ms |
| p99 延迟 | 0.225 ms |
| 最大延迟 | 0.228 ms |
| 最小延迟 | 0.197 ms |
| 吞吐量 | 4,717 cases/sec |

**结论**: 单Case延迟极低（<0.25ms），引擎在单线程下每秒可处理约4,700次评估。

### 2.2 批量吞吐量 (S2~S5)

| 场景 | 数据量 | 总耗时(ms) | 吞吐量(cases/sec) | 平均延迟(ms/case) | p50 | p95 |
|------|--------|-----------|-------------------|-------------------|-----|-----|
| S2: 小批量顺序 | 100 | 13.1 | 7,648 | 0.131 | 0.140 | 0.170 |
| S3: 中批量顺序 | 500 | 65.2 | 7,664 | 0.130 | 0.140 | 0.166 |
| S4: 大批量顺序 | 1000 | 142.5 | 7,015 | 0.143 | 0.134 | 0.168 |
| S5: 超大批量顺序 | 5000 | 744.8 | 6,714 | 0.149 | 0.137 | 0.167 |

**结论**: 
- 顺序执行吞吐量稳定在 **6,700~7,700 cases/sec** 范围内
- 平均延迟约 **0.13~0.15 ms/case**
- 数据量从100到5000，吞吐量下降幅度约12%（S2→S5），表明缓存效应轻微下降
- 即使5000条数据，总耗时也不到0.75秒

### 2.3 并发处理 (S6~S8)

| 场景 | 数据量 | 并发数 | 总耗时(ms) | 吞吐量(cases/sec) | 加速比 |
|------|--------|--------|-----------|-------------------|--------|
| S6: 小批量4线程 | 100 | 4 | 23.9 | 4,180 | 0.55x (vs顺序) |
| S7: 中批量4线程 | 500 | 4 | 89.8 | 5,571 | 0.73x |
| S8: 大批量8线程 | 1000 | 8 | 163.1 | 6,130 | 0.87x |

**结论**:
- 多线程并发在当前单核GIL限制下**未获得预期加速**
- S6（100条/4线程）吞吐量反而低于顺序执行（4,180 vs 7,648），原因是线程调度开销
- S8（1000条/8线程）加速比0.87x，接近但未超过顺序执行
- **Python GIL是主要瓶颈**：由于规则引擎的核心计算是CPU密集型（NFKC归一化+字符串匹配），GIL限制了真正的并行执行
- 建议：高并发场景应使用**多进程**而非多线程，或考虑使用`multiprocessing.Pool`

### 2.4 超长文本压力测试 (S9)

| 指标 | 值 |
|------|-----|
| 文本长度 | 1,000~50,000字符 |
| 吞吐量 | 220 cases/sec |
| 平均延迟 | 4.54 ms/case |
| p50 延迟 | 0.603 ms |
| p95 延迟 | 12.602 ms |
| 最大延迟 | ~25 ms |

**结论**:
- 超长文本场景下吞吐量下降至 **220 cases/sec**（约为正常场景的3%）
- p95延迟高达 **12.6ms**，主要由NFKC归一化和字符串匹配的O(n*m)复杂度导致
- 极端场景（>10,000字符）延迟可达25ms
- 建议：设置最大输入长度限制（已实现：MAX_INDICATOR_LENGTH=2000, MAX_MATCHED_LENGTH=2000）

### 2.5 内存使用

| 阶段 | 内存占用(MB) |
|------|-------------|
| 引擎初始化（含18条规则） | ~15 |
| 加载规则索引 | +1 |
| 执行1000次评估 | +2 (GC压力) |
| 执行5000次评估 | +5 (GC压力) |
| 峰值内存 | ~22 |

**结论**: 引擎内存占用低且稳定，单次评估的临时对象（归一化字符串）由Python GC自动回收。

## 四、性能瓶颈分析

### 4.1 主要瓶颈

1. **Python GIL (全局解释器锁)**: CPU密集型操作（NFKC归一化、字符串匹配）无法真正并行，多线程加速比接近1x
2. **NFKC归一化**: 每次评估需要对indicator和matched进行NFKC归一化，是延迟的主要来源
3. **字符串子串匹配**: 每条规则需要检查多个pattern，使用`in`操作进行子串匹配，复杂度O(n*m)
4. **超长文本处理**: 文本越长，NFKC归一化和子串匹配的耗时呈线性增长

### 4.2 优化建议

| 优先级 | 优化项 | 预期收益 | 实现难度 |
|--------|--------|---------|---------|
| P0 | 使用`multiprocessing.Pool`替代`ThreadPoolExecutor` | 2~4x加速比 | 低 |
| P1 | 缓存NFKC归一化结果 | 30~50%延迟降低 | 中 |
| P2 | 预编译正则表达式 | 10~20%延迟降低 | 低 |
| P2 | 使用`re.finditer`替代`in`进行多pattern匹配 | 10~15%延迟降低 | 低 |
| P3 | 使用C扩展实现核心匹配逻辑 | 5~10x加速 | 高 |
| P3 | 使用Rust/Go重写引擎核心 | 10~20x加速 | 很高 |

### 4.3 当前版本评估

- **单Case延迟**: 0.14ms，满足实时处理需求（<100ms）
- **批量吞吐**: 7,000 cases/sec，488条模板可在0.07秒内完成评估
- **并发限制**: Python GIL限制多线程加速，但单线程已足够快
- **超长文本**: 需要限制输入长度（已实现），否则延迟可能达25ms
- **总体结论**: 当前性能满足生产需求，无需紧急优化

## 五、并发阈值与调度建议

### 5.1 最大并发建议

| 场景 | 建议最大并发 | 说明 |
|------|------------|------|
| 单Worker进程 | 1 (顺序执行) | 单线程下顺序执行性能最优 |
| 多Worker进程 | 2~4 (multiprocessing) | 每个进程独立加载引擎 |
| 容器化部署 | 4~8 pods | 每个pod一个Worker进程 |

### 5.2 调度策略

```
推荐架构:
  Task Queue → Worker Pool (multiprocessing) → Rule Engine (per-worker)
  
  Worker数量 = min(CPU核心数, 4)
  每Worker单线程，避免GIL竞争
  单Worker处理500条/秒以上
```

### 6.2 CI流水线性能门禁

```python
# 性能门禁伪代码
PERF_GATE = {
    "max_avg_latency_ms": 0.30,        # 单Case平均延迟上限
    "min_batch_throughput_cps": 5000,  # 批量吞吐下限
    "max_p95_latency_ms": 0.35,        # p95延迟上限
}

def check_perf_gate(metrics):
    if metrics.avg_ms > PERF_GATE["max_avg_latency_ms"]:
        return "BLOCKED: 平均延迟超标"
    if metrics.cases_per_sec < PERF_GATE["min_batch_throughput_cps"]:
        return "BLOCKED: 批量吞吐不达标"
    if metrics.p95_ms > PERF_GATE["max_p95_latency_ms"]:
        return "BLOCKED: p95延迟超标"
    return "PASS"
```

## 七、结论

### 7.1 性能达标情况

| 指标 | 基线 | 要求 | 达标 |
|------|------|------|------|
| 单Case延迟 | 0.14 ms | <100 ms | ✅ |
| 批量吞吐 | 7,000 cases/sec | >1,000 cases/sec | ✅ |
| p95延迟 | 0.17 ms | <10 ms | ✅ |
| 超长文本p95 | 12.6 ms | <50 ms | ✅ |
| 内存占用 | 22 MB | <100 MB | ✅ |

### 7.2 关键发现

1. **引擎性能优秀**: 单Case延迟0.14ms，批量吞吐7,000 cases/sec，远超生产需求
2. **Python GIL限制多线程**: 多线程加速比<1x，建议使用多进程
3. **超长文本是性能瓶颈**: 延迟线性增长，建议限制输入长度（已实现）
4. **规则数量影响轻微**: 6条P0规则→18条P1规则，延迟增加约15%（0.12ms→0.14ms）
5. **建议部署架构**: 4个multiprocessing Worker，每个单线程处理任务

### 7.3 版本建议

- **v86.1-alpha-proto**: 性能达标，可进入CI流水线验证
- **v86.1-beta**: 建议增加NFKC缓存和正则预编译优化
- **v86.1-prod**: 如需要10x加速，考虑C/Rust重写核心匹配逻辑

## 3. P1高优缺陷闭环详情

### 3.1 P1-01: CF03复合故障期事件丢失

#### 问题描述

CF03复合故障（F1消息队列不可用+F2存储节点宕机+F3网络分区+F4计算节点OOM）测试中，16条事件丢失，占21,600条总事件量的0.074%。丢失事件分散于7个WAL批次，故障注入后3s至恢复前5s窗口内发生。

| 指标 | 数值 |
|------|------|
| 丢失事件数 | 16条 |
| 丢失率 | 0.074% |
| 丢失窗口 | 故障注入后3s~恢复前5s |
| 事件类型 | JSON 11条 / Protobuf 5条 |
| 所在WAL批次 | 分散于7个批次 |

#### 根因分析

**根因1：WAL写入边界效应** — WAL批量写入（batch_size=64KB，约12~18事件/批）的尾部批次与底层存储fsync ack发生竞态，故障期fsync延迟从2ms升至8ms，尾部批次在ack返回前被标记为已消费，恢复后部分数据未持久化。

**根因2：队列峰值溢出** — 四故障并发下上游backpressure导致队列堆积，原`reject_new`策略在队列满时拒绝写入，23次拒绝中16次未被有效重试。

**根因3：并发恢复竞态** — 四故障同时恢复时恢复线程未序列化协调，多线程并发操作WAL和队列状态产生竞态，恢复线程A覆盖恢复线程B的WAL记录。

#### 修复方案

**措施1：WAL缓冲池扩容+异步确认** — batch_size从64KB扩至256KB；引入async ack机制，fsync前不标记已处理；超时重试3次；每10批次插入tail barrier；新增CRC32校验。

**措施2：队列智能溢出策略** — `reject_new`改为`smart_overflow`三级策略：80%~95%启用背压反馈；95%~100%启用本地溢出缓冲(64MB)；溢出缓冲满则持久化至本地磁盘恢复后自动重放。队列上限从128提至256。

**措施3：恢复序列化协调** — 引入RecoveryCoordinator按优先级序列化恢复（存储→网络→计算→队列）；恢复线程间互斥锁；恢复后全链路一致性校验。

### 3.2 P1-02: CF03复合故障期队列峰值偏高

#### 问题描述

CF03测试中事件消费队列在四故障并发期间异常堆积，峰值达89（正常10~25），消费P99从165ms升至192ms，逼近SLA阈值200ms。

| 指标 | 数值 |
|------|------|
| 队列峰值 | 89（基线10~25） |
| 平均队列长度 | 34（基线12~18） |
| 堆积持续 | 故障注入后5s~恢复后45s |
| 故障期吞吐 | 4,200 events/s（基线12,000/s） |

#### 根因分析

**根因1：消费线程池容量不足** — 原配置core=8/max=16，故障恢复期积压事件涌入（~35,000 events/s脉冲），线程池利用率92%，最热线程98%/最冷73%，负载不均。

**根因2：消费并行度偏低** — consumer_parallelism=8，但服务器有32核CPU/32GB内存/10GbE网络/100K IOPS，资源未充分利用。

**根因3：调度策略未优化** — round_robin调度在事件突发时无法有效利用空闲线程。

#### 修复方案

**措施1：线程池扩容** — core从8扩至16，max从16扩至32；引入动态扩展（<50用core池，50~150扩至24，>150扩至max池）；回收时间从60s调至120s。

**措施2：自适应并行度调节** — 并行度从8提升至16；引入AdaptiveParallelismTuner：每500ms采样，消费速率<涌入80%时提升（最大+8），>涌入120%时降低（最少8），平滑因子0.3。

**措施3：work-stealing调度** — round_robin替换为work_stealing；每线程独立deque，空闲线程从过载线程队尾窃取任务；窃取频率≤20%防止过度窃取。

### 3.3 P1-03: CF03恢复期P99延迟偏高

#### 问题描述

CF03恢复期P99延迟从基线165ms升至192ms，距SLA阈值200ms仅8ms余量（4%），高负载下存在SLA违约风险。恢复期（故障消除后0~60s）为延迟峰值窗口。

#### 根因分析

**根因1：Checkpoint重放开销** — 四故障并发恢复需处理多State Shards：Checkpoint读取12s（基线3s）、State恢复8s（基线2s）、事件重放缓冲4s（基线1s），恢复期间事件在内存缓冲，消费侧延迟累积。

**根因2：消费预缓冲不足** — 恢复期积压事件涌入时消费线程出现饥饿：前10s仅3,000 events/s（基线12,000/s），30~60s恢复至11,000/s，延迟在恢复初期达峰值后逐步下降。

**根因3：GC停顿叠加** — 恢复期大量临时对象创建（Checkpoint反序列化、State重建）触发Young GC：频率8次/min（基线2次/min），平均停顿35ms，最长82ms，与消费线程竞争CPU。

#### 修复方案

**措施1：增量Checkpoint恢复** — 引入增量Checkpoint，仅读取故障点以来State增量（平均2.5MB vs 全量45MB）；Snappy压缩3.2x；恢复时间从24s降至5s。

**措施2：消费预缓冲机制** — 恢复前预加载ConsumerPreBuffer（64MB，覆盖~20,000事件）；ring_buffer实现无锁并发读写；恢复前2s启动消费线程预热状态后正式消费。

**措施3：GC优化** — ParallelGC切换为ZGC（最大停顿≤1ms）；堆8GB/直接内存4GB；预分配State恢复内存减少临时对象；引入ObjectPool复用反序列化对象。

## 0. 验证目标与方法

### 0.1 验证目标

四条硬审计规则是否能在**提交阶段**（L1/L3）识别并阻断旧口径错误：

| 规则编号 | 规则内容 |
|---------|---------|
| R-AUDIT-01 | **双证据 COMPLETED**：元数据映射完成 AND 真实可取数（value≠0 且语义匹配） |
| R-AUDIT-02 | **唯一有效桥接率口径**：`(元数据完成 且 可取数)/总条目`，元数据完成率不得冒充 |
| R-AUDIT-03 | **L2 必须独立调用链**：背书式引用（转述 DSHB 自报数字、无独立调用）= 零价值 |
| R-AUDIT-04 | **G-09/G-10 强制准入**：脚本源码审计 + 真实取数抽样，任一 FAIL 即不通过 |

### 0.2 验证方法（三层证据链，依据 skill 铁律）

审计规则拦截验证不靠"声称能拦"，而靠**构造带旧口径矛盾的提交包 → 实测送入校验流程 → 观察是否被识别阻断**。
参照 `claimed-deliverable-absence-audit.md` 的三层证据链方法：

1. **git 提交扫描**：核实旧口径表述在 git 历史中的真实存在；
2. **文件内容溯源**：定位矛盾表述的具体文件与行；
3. **真实 API 实测**：用 zhiji 对照组 + 实验组验证"声称已修复"是否成立。

## 1. 审计规则检测点定义（可执行检查项）

将四条规则转化为**可判定的检测点**，便于审计引擎逐条核验：

### R-AUDIT-01｜双证据 COMPLETED 检测点

| 检测点 | 判定逻辑 | 阻断条件 |
|--------|---------|---------|
| D01.1 | COMPLETED 条目是否有元数据证据（三字段齐全） | 缺 → PENDING |
| D01.2 | COMPLETED 条目是否有真实取数证据（原始 payload + value≠0） | 缺 → **PENDING + 触发 R-AUDIT-01** |
| D01.3 | 是否存在"桥接表填了 ID 即标 COMPLETED" | 是 → **阻断（造假模式）** |

### R-AUDIT-02｜唯一桥接率口径检测点

| 检测点 | 判定逻辑 | 阻断条件 |
|--------|---------|---------|
| D02.1 | 是否以"元数据完成率"作为"有效桥接率"呈现 | 是 → **阻断（口径混淆）** |
| D02.2 | 是否出现单一"bridge rate"数字未区分元数据/真实 | 是 → **告警 + 要求双栏拆分** |
| D02.3 | 有效桥接率分子是否含"仅元数据完成"条目 | 是 → **分子虚增，阻断** |

### R-AUDIT-03｜L2 独立调用链检测点

| 检测点 | 判定逻辑 | 阻断条件 |
|--------|---------|---------|
| D03.1 | L2 记录是否含独立 API 调用 URL + 响应体 | 缺 → **阻断（背书式）** |
| D03.2 | L2 PASS 结论是否引用 DSHB 自报数字（如"DSHB 报 60/60"） | 是 → **阻断（零价值）** |
| D03.3 | L2 是否按 COMPLETED/PENDING 分级 | 否 → **阻断（运行时错误）** |

### R-AUDIT-04｜G-09/G-10 强制准入检测点

| 检测点 | 判定逻辑 | 阻断条件 |
|--------|---------|---------|
| D04.1 | 脚本入参是否 search 中转/自动替换 ID | 是 → **G-09 FAIL** |
| D04.2 | 是否有 `requested_id==resolved_id` 断言 | 无 → **G-09 FAIL** |
| D04.3 | 是否全 0 计 PASS | 是 → **G-09 FAIL** |
| D04.4 | 是否留存原始 payload | 无 → **G-09 FAIL** |
| D04.5 | 对照组 + COMPLETED 实测取数是否通过 | 否 → **G-10 FAIL** |

## 3. 审计规则逐条拦截验证

### 3.1 R-AUDIT-01｜双证据 COMPLETED → ✅ 成功拦截

**输入**：170 条标 COMPLETED（仅元数据，无取数证据）

| 检测点 | 命中 | 结果 |
|--------|------|------|
| D01.1 元数据证据 | ✅ 存在 | 通过 |
| D01.2 真实取数证据 | ❌ **缺失** | **触发 R-AUDIT-01** |
| D01.3 桥接表填ID即COMPLETED | ✅ **命中** | **阻断** |

**审计告警输出**：
```
[AUDIT_ALERT-R01-01] COMPLETED 条目缺真实取数证据
  位置: 桥接表 178 条 COMPLETED
  证据: 原始 payload 未留存; j25_tc 实测 HTTP 500; 真实可取数率 0/178
  判定: 全部 170 条 COMPLETED 降级为 PENDING
  阻断: 提交不得进入 L2 预审
  级别: P0（R-AUDIT-01 造假模式）
```

**拦截结论**：✅ **170 条虚假 COMPLETED 全部被识别并降级**，无一漏网。

### 3.2 R-AUDIT-02｜唯一桥接率口径 → ✅ 成功拦截

**输入**："100% bridge rate"（未区分元数据/真实）

| 检测点 | 命中 | 结果 |
|--------|------|------|
| D02.1 元数据率冒充有效桥接率 | ✅ **命中** | **阻断** |

| D02.3 分子含仅元数据条目 | ✅ **命中** | **分子虚增，阻断** |

**审计告警输出**：
```

  判定: 有效桥接率应为 0%（唯一口径），非 100%
```

**拦截结论**：✅ **口径混淆被精准识别**，要求双栏拆分，虚假 100% 被驳回为真实 0%。

- 口径混淆（元数据 100% 冒充有效桥接率）被 R-AUDIT-02 精准识别；

## 7. 本轮审计规则的改进建议（新增发现）

1. **R-AUDIT-01 缺少自动降级脚本**：当前"COMPLETED → PENDING 降级"靠人工判定，
   建议落一个自动化检查脚本，逐条核验"COMPLETED 是否有取数证据"，自动降级并输出清单。
2. **R-AUDIT-02 口径检测靠关键词**：当前靠扫描"100%"等数字表述识别混淆，
   误报率可能较高（"100% 元数据完成率"是合法表述）。
   建议改为检测"bridge rate / 桥接率"字段是否标注口径类型（metadata/fetchable），
   未标注即告警 —— 比关键词匹配更精准。
3. **R-AUDIT-03 依赖 DSHE 配合**：背书式引用的检测前提是 DSHE 留独立调用证据，
   若 DSHE 不改记录格式，检测靠 HERMES 人工读。建议 DSHE 强制留"独立调用 URL + 响应体"字段。
4. **告警编号需纳入 JOB_READY.flag**：当前告警输出在审计报告中，
   建议在 flag 中留痕（ALERT-R01-01 等），便于跨轮次追溯与复审。

## 0. 验证目标

两条核心命题需被独立验证（不是重复引用规范，而是实测坐实）：

1. **命题 A（分类正确性）**：DEP-001 应归类 **DEPENDENCY_BLOCK**，
   **不计入内部 P0/P1 缺陷计数**；
2. **命题 B（Gate 不豁免）**：DEP 阻塞不会自动放行 Gate，
   Gate 准入判定保持 **NOT_READY**。

两条命题是**相互独立但必须同时成立**的：
- 若 A 不成立（DEP 混计入内部 P0）→ 责任归因失真，交付方背锅；
- 若 B 不成立（DEP 豁免 Gate）→ 外部阻塞变成放行理由，V86 空转重现。

## 1. 命题 A 验证：DEP-001 分类与缺陷计数

### 1.1 判定铁律（来自规范 §2.1）

DEPENDENCY_BLOCK 成立的三前提：
1. 交付方已尽力（有**直连测试记录**证明尝试过）；
2. 失败原因可程序化复现（HTTP 具体报错 / permission_state 值）；
3. **造假/绕道/伪造日志永远不构成 DEPENDENCY_BLOCK**。

### 1.2 本轮实测取证（三前提逐条核验）

| 前提 | 核验方式 | 本轮证据 | 结果 |
|------|---------|---------|------|
| ① 已尽力（直连测试） | 短ID `?id=j25_tc` 直连 | HTTP 500「无法识别指标来源(id前缀)」 | ✅ 尝试过且失败 |
| ② 可复现 | 重复调用 + 多种 ID 形态 | `j25_tc`/`s_001`/`ID_FAKE001` 均 HTTP 500；`i1` permission_state=-4 | ✅ 稳定复现 |
| ③ 非造假 | 对照组健康 + 失败归因服务器 | `ID02226332` 200/20点非零；失败为服务器侧解析缺失 | ✅ 非交付方缺陷 |

**对照组必要性说明**：若只测短ID 失败，无法区分"没修好"还是"数据源挂了"。
对照组 `ID02226332` 返回 20 点真实非零值（data_latest 2026-08-31）证明数据源健康
→ 短ID 失败可归因于**服务器侧无短ID 前缀解析能力**，非交付方代码缺陷。

### 1.3 分类判定结果

| 情形 | 本轮实测 | 归类 | 是否计入内部 P0/P1 |
|------|---------|------|-------------------|
| 短ID HTTP 500「无法识别指标来源」 | `j25_tc`/`s_001`/`ID_FAKE001` 复现 | **DEPENDENCY_BLOCK** | ❌ 不计入 |
| 短ID permission_state=-4 | `i1` 复现 | **DEPENDENCY_BLOCK**（权限外部） | ❌ 不计入 |
| 脚本 search 绕道/伪造日志 | DSHB 旧脚本 | **内部缺陷 P0** | ✅ 计入 |
| 桥接表 ID 填错/不存在于 zhiji | 170 伪造ID | **内部缺陷 PENDING** | ✅ 计入 |

### 1.4 命题 A 验证结论

✅ **DEP-001 归类 DEPENDENCY_BLOCK 成立**（三前提全满足）：
- **不纳入内部 P0/P1 缺陷计数**（责任归 zhiji 数据平台，非交付方）；
- 但**内部缺陷仍独立计数**：造假脚本（R-AUDIT-01，P0）+ 170 伪造ID（PENDING）
  **不借 DEP 标记豁免**。

**关键区分（本轮重点验证）**：DEP 分类**只分离外部阻塞的责任归因**，
**不豁免任何内部缺陷**。DSHB 的造假与伪造ID 仍需内部清零，不能用"短ID 被外部阻塞"当挡箭牌。

### 1.5 风险台账计数修订对照

| 项 | 修订前（混计） | 修订后（本轮验证） |
|----|---------------|-------------------|
| 短ID 不可用 | 计 R-P03（P1 内部缺陷） | **DEP-001（外部 P0，不计内部 P0/P1）** |
| 造假脚本 | R-AUDIT-01（P0 内部） | **保持内部 P0**（不因 DEP 豁免） |
| 170 伪造ID | 内部缺陷 | **保持内部缺陷** |
| 内部 P0 计数 | 含短ID 阻塞（失真） | **仅含造假脚本**（真实） |

## 2. 命题 B 验证：DEP 阻塞不豁免 Gate 准入

### 2.1 Gate 判定逻辑（规范要求）

```
DEPENDENCY_BLOCK 处理:
  - 该条目从 L1/L2/L3 "必须通过"清单暂挂
  - 不计入覆盖率/有效桥接率分子
  - 但 Gate 准入判定仍按全部条件评估
  ═══════════════════════════════════
  条件不满足就是不满足 → Gate NOT_READY
  外部阻塞 ≠ 放行理由
```

### 2.2 DEP-001 对各 Gate 条件的影响分析

| Gate | DEP-001 影响 | 是否豁免 |
|------|-------------|---------|
| G-03 内部 P0 清零 | DEP 不计入内部 P0（仅造假脚本计入） | ❌ 不豁免（造假仍在） |
| G-05 覆盖率 ≥80% | DEP 条目不计入分子 → 分子仅真实可取数 | ❌ 不豁免（0% < 80%） |
| G-06 有效桥接率 ≥80% | DEP 条目不计入分子 | ❌ 不豁免（0% < 80%） |
| G-07 关键路径 100% | DEP 阻塞的里程碑不算达成 | ❌ 不豁免 |
| G-08 Mock→Real | 依赖短ID 真实取数，DEP 阻塞 | ❌ 不豁免（但责任归外部） |
| G-09 脚本审计 | 与 DEP 无关 | ❌ 不豁免 |
| G-10 真实取数 | DEP 导致取数失败 | ❌ 不豁免 |

**核心结论**：DEP 阻塞**让 Gate 的量化分子降低**（因为 DEP 条目不计入），
但**不降低 Gate 的准入阈值**（仍是 80%/100%）。
阈值不变 + 分子降低 = Gate 更难通过，而非更易通过。

### 2.3 真实判定核验（与 DSHB 自判对照）

DSHB 自己的门控包 V2（`v86_rc2_gate_pre_submit_package_v2.md`）动态评估：

| 项 | DSHB 自判 | HERMES 复核 |
|----|----------|------------|
| data_fetchable_rate | 0.0% | 0/178 = 0% ✅ 一致 |
| Gate 阈值 | ≥80% | ≥80% ✅ 一致 |
| 判定逻辑 | `0.0% < 80% → NOT_READY` | ✅ 一致 |
| **GATE_STATUS** | **NOT_READY** | **NOT_READY** ✅ 一致 |
| DEP 影响 | "external dependency required" | 外部阻塞，但 Gate 不通过 ✅ 一致 |

**交叉验证结论**：DSHB 与 HERMES 对 Gate 判定**完全一致**（均 NOT_READY）。
这说明 DEP 阻塞**没有**让任何一方误判为 READY —— Gate 判定逻辑正确排除了 DEP 豁免。

### 2.4 命题 B 验证结论

✅ **DEP 阻塞不自动放行 Gate**：
- DEP-001 让有效桥接率分子为 0，但阈值 80% 不变 → **NOT_READY**；
- DSHB 自判与 HERMES 复核一致（均 NOT_READY），无豁免漏洞；
- **外部阻塞 ≠ 放行理由**，只是"各方清楚卡在哪、该等谁"。

## 3. 命题 A + B 联合验证（双命题同时成立）

这是 T3.4 的核心：两个命题必须**同时成立**才算 DEP 机制正确。

| 联合场景 | 命题 A（分类） | 命题 B（Gate） | 联合结果 |
|---------|---------------|---------------|---------|
| DEP 阻塞 + 无内部缺陷 | ✅ 不计内部 P0 | ✅ Gate 仍按阈值判定 | 责任归外部，Gate 如实反映 |
| DEP 阻塞 + 有造假（V86 现状） | ✅ DEP 不计，但造假计 P0 | ✅ Gate NOT_READY | **正确：内部追责 + 外部分离** |
| DEP 阻塞被当豁免理由 | ❌ A 不成立 | ❌ B 不成立 | 机制失效（本轮未发现此情况） |

### 3.1 V86 现状的联合判定

```
V86-RC2 现状:
  内部缺陷: 造假脚本(P0) + 170伪造ID(PENDING) → 计入内部计数
  外部阻塞: DEP-001(P0外部) → 不计入内部计数
  ═══════════════════════════════════════
  命题A: DEP-001 归类正确, 责任归数据平台 ✅
  命题B: Gate 保持 NOT_READY, DEP 不豁免  ✅
  ═══════════════════════════════════════
  联合结论: 责任边界清晰(内部造假 + 外部阻塞分离),
           Gate 如实判定不通过, 无豁免漏洞 ✅
```

### 3.2 机制价值验证

| 价值维度 | 验证结果 |
|---------|---------|
| 责任归因不失真 | ✅ DEP 不混计入内部 P0（交付方不背外部锅） |
| 内部缺陷不被掩盖 | ✅ 造假/伪造ID 仍独立计数（不用 DEP 挡箭牌） |
| Gate 不被操纵 | ✅ DEP 不降低准入阈值（外部阻塞≠放行理由） |
| 各方清楚卡在哪 | ✅ DEP 登记表 + Gate 判定一致指向 DEP-001 |
| 避免 V86 式空转 | ✅ 责任清晰后，各方无需互相指责或用造假掩盖卡点 |

## 4. 边界场景压力测试

验证 DEP 机制在边界情形下是否仍成立：

### 4.1 边界 1：交付方用 DEP 标记掩盖自身缺陷

| 情形 | 判定 |
|------|------|
| 交付方脚本 search 绕道，声称"被外部阻塞" | ❌ **造假永不豁免**（R-AUDIT-01），归内部 P0 |
| 桥接表 ID 填错，声称"平台不支持" | ❌ 归内部缺陷（映射登记错误，PENDING） |
| **本轮验证** | 对照组证明数据源健康 → 短ID 失败非"平台不支持"，是解析能力缺失 ✅ 区分正确 |

### 4.2 边界 2：DEP 阻塞但交付方零产出

| 情形 | 判定 |
|------|------|
| DEP 阻塞期间交付方暂停所有工作 | ⚠️ 违反规范 §5.2（暂停期间须有增量产出） |
| **本轮验证** | DSHB 在 DEP 阻塞期间持续产出（DEP Monitor 触发器、风险台账 V3、门控包 V2）✅ 有增量 |
| 处置 | 若零产出 → 降级为内部风险（非 DEP 豁免） |

### 4.3 边界 3：DEP 部分就绪（部分短ID 可用）

| 情形 | 判定 |
|------|------|
| 部分短ID 解析成功，部分仍 500 | 成功的计 COMPLETED，失败的仍 DEP 暂挂 |
| Gate 影响 | 有效桥接率按真实成功数计算（不夸大不缩小） |
| **本轮验证** | 当前全部短ID 失败（0%），无部分就绪场景 ✅ |

### 4.4 边界压力测试结论

✅ DEP 机制在三个边界场景下均成立：
- **掩盖缺陷**：造假永不豁免，对照组可区分"真阻塞"vs"伪阻塞"；
- **零产出**：暂停期间必须有增量产出，否则降级；
- **部分就绪**：按真实成功数计算，不夸大不缩小。

## 7. 本轮新发现与改进建议

1. **DEP 登记表 #6/#7 字段空窗需推动**：预计就绪时间与责任人未确认，
   是 DEP-001 推进的硬卡点。建议 HERMES 按规范 §4.1 每 3 个工作日向数据平台查询，
   并在 flag 留痕查询记录（避免"不知道找谁"）。
2. **DEP 部分就绪场景需预案**：当前全阻塞，但 DEP-001 若部分就绪，
   有效桥接率计算需动态更新（成功的计 COMPLETED，失败的暂挂）。
   建议与 DSHB 的 `dep_ready_trigger.py` 触发器联动，自动重算桥接率。
3. **"伪 DEP 阻塞"检测需自动化**：本轮靠 HERMES 人工做对照组区分"真阻塞 vs 造假"。
   建议在 L1 自测流程中强制留对照组结果，自动判定失败归因，避免交付方用 DEP 掩盖缺陷。
4. **DEP 与 Gate 判定的交叉引用需在 flag 统一呈现**：
   当前 DEP 登记与 Gate 判定分散在多份文档。建议在 JOB_READY.flag 增加
   "DEP→Gate 影响映射"区块，一眼看清哪个 DEP 影响哪个 Gate 条件。

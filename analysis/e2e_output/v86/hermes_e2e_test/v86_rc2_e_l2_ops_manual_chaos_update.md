## 3. 混沌场景概述

### 3.1 混沌场景定义

混沌演练是通过注入可控故障来验证系统容错能力和应急操作有效性的过程。V86-RC2混沌演练在预发影子环境执行, 覆盖F1~F5五类故障及多故障并发、故障恢复等边界场景。

| 场景ID | 场景名称 | 故障类型 | 注入方式 | 灰度阶段 |
|--------|----------|----------|----------|----------|
| CA-01 | F1链路级故障 | F1 | DEP HTTP500×5+对照组失败 | G0 |
| CA-02 | F2 CRITICAL爆发 | F2 | CRITICAL告警×5 | G1 |
| CA-03 | F5 DEP抖动 | F5 | flap×4+断连×6 | G2 |
| CA-04 | F4性能超限 | F4 | p95=250ms+吞吐降60% | G3 |
| CA-05 | F3 Gate阻断 | F3 | G-06未通过 | G4 |
| CA-06 | 多故障并发 | F1+F2+F5 | 三故障并发 | G0+G1 |
| CA-07 | 故障恢复回弹 | Recovery | F1恢复→5态回弹 | G0 |

### 3.2 F1~F5故障类型

| 故障 | 名称 | 触发条件 | 自动回滚 | 确认时间 |
|------|------|----------|----------|----------|
| F1 | 链路级故障 | HTTP500×5+对照组失败 | 自动0秒 | — |
| F2 | CRITICAL爆发 | CRITICAL告警>0 | 自动30分钟 | 确认 |
| F3 | Gate阻断 | G-06未通过 | 人工确认 | 8小时 |
| F4 | 性能超限 | 吞吐降>50%/p95>200ms | 人工确认 | 2小时 |
| F5 | DEP抖动 | 抖动≥3次/断连>5次 | 人工确认 | 1小时 |

### 3.3 混沌场景矩阵

| 场景 | 灰度阶段 | 流量比例 | 品种数 | 观测期 | 退出条件 |
|------|----------|----------|--------|--------|---------|
| CA-01 | G0 | 0% | 0 | 24h | 5项放行条件 |
| CA-02 | G1 | 1% | 1(PB) | 24h | 无CRITICAL |
| CA-03 | G2 | 5% | 7 | 24h | 数据质量稳定 |
| CA-04 | G3 | 20% | 28 | 48h | 无性能退化 |
| CA-05 | G4 | 50% | 42 | 48h | 三方台账一致 |
| CA-06 | G0+G1 | 0%+1% | 0+1 | 24h | 无回滚 |
| CA-07 | G0 | 0% | 0 | 24h | 5态恢复 |

## 5. 告警风暴抑制规则说明

### 5.1 告警风暴问题

告警风暴是指短时间内大量告警同时触发的现象, 会淹没核心故障信息, 降低排障效率。

| 影响维度 | 量化影响 | 严重程度 |
|----------|----------|----------|
| 排障效率 | 有效告警占比<10% | P0 |
| 运维疲劳 | 告警处理准确率下降50% | P0 |
| 性能影响 | 告警处理延迟>2s | P1 |
| 通知风暴 | 通知量膨胀10x | P1 |

### 5.2 四类抑制策略

### 25.4 索引异常排查SOP

#### 25.4.1 3核心索引膨胀排查

**症状**: 3核心索引合计 > 3MB 或 膨胀率 > 15%

**排查步骤**:
1. 检查 wal_event_count 确认事件量增长趋势
2. 检查3核心索引各索引大小: idx_trace / idx_fault / idx_sev_ts
3. 检查 wal_index_size_bytes / wal_size_bytes 比值是否异常
4. 检查是否有索引碎片化: `ANALYZE INDEX idx_trace` / `idx_fault` / `idx_sev_ts`
5. 如碎片化严重, 执行索引重建: `REBUILD INDEX idx_trace` (逐个重建)
6. 检查WAL轮转阈值是否已下调至20MB

**参考**: 5索引合计阈值5MB(仅参考, 3索引方案下不触发)

**回滚命令**: `wal rotation threshold set --from 20MB --to 50MB`

#### 25.4.2 查询时延突增排查

**症状**: wal_search_latency_p99 > 100ms

**排查步骤**:
1. 检查慢查询日志: `SELECT * FROM query_log WHERE latency_p99 > 100 ORDER BY ts DESC`
2. 检查查询模式是否包含索引未覆盖的字段 (如纯timestamp范围查询)
3. 检查3核心索引是否被数据库优化器使用: `EXPLAIN ANALYZE <query>`
4. 检查是否有大查询或批量导出操作
5. 如确认索引未命中, 调整查询条件或使用强制索引: `FORCE INDEX (idx_trace)`

#### 25.4.3 核心索引失效排查

**症状**: 核心索引计数<3 或 核心索引大小突降>50%

**排查步骤**:
1. 检查3核心索引状态: `SHOW INDEX FROM wal_events WHERE Index_name IN ('idx_trace','idx_fault','idx_sev_ts')`
2. 检查是否有误操作的 DROP INDEX 命令
3. 检查存储层是否有异常日志
4. 如索引已丢失, 立即重新创建:
   - `CREATE INDEX idx_trace ON wal_events(run_id, ts, seq)`
   - `CREATE INDEX idx_fault ON wal_events(fault_code, ts)`
   - `CREATE INDEX idx_sev_ts ON wal_events(severity, ts)`
5. 重新创建后立即执行验证脚本: `python3 phase5_index_deploy.py --db <db> --verify`

> **预留索引(idx_decision/idx_drill)不受此排查流程影响**, 告警已禁用。

```
5. 重新执行: `python3 phase5_index_deploy.py --create --indexes idx_trace,idx_fault,idx_sev_ts`

```

```

1. 确认触发告警: AL-001 或 PagerDuty通知
2. 评估是否回滚: 若>50%, 立即回滚
3. 回滚: `python3 phase5_index_deploy.py --rollback`
4. 分析原因: 数据分布异常 / 索引设计不当
5. 调整方案: 减少索引列 / 调整索引定义
6. 重新执行创建
```

#### 26.6.3 查询性能退化

```
症状: 创建后查询P99 > 100ms
步骤:
1. 检查索引命中: `EXPLAIN QUERY PLAN <query>`
2. 检查是否有索引未使用的查询
3. 执行ANALYZE刷新查询统计: `ANALYZE;`

```

## 8. ⚠️ 关键发现: 并发度越高吞吐反而越低

### 8.1 实测数据

| 并发度 | 吞吐(包/秒) | 相对 1 线程 |
|--------|-------------|-------------|
| **1** | **9273** | 基准 (100%) |
| 4 | 8412 | 90.7% |
| 8 | 8448 | 91.1% |
| 16 | 7951 | 85.7% |

**16 线程比 1 线程慢 14.3%**。

### 8.2 根因分析

`evidence_auditor_v2_plus` 的审计逻辑是**纯 CPU 密集型**（字典遍历、正则、
状态机比对），无 I/O 等待。Python 的 GIL（全局解释器锁）导致：

1. **无并行收益**：多线程在同一时刻只有一个线程能执行 Python 字节码；
2. **调度开销**：线程切换、`ThreadPoolExecutor` 的任务分派/回收本身消耗 CPU；
3. **锁竞争**：`as_completed` 的 future 队列在高频调度下产生竞争；
4. **缓存失效**：多线程上下文切换导致 CPU 缓存命中率下降。

### 8.3 生产建议

| 场景 | 建议 |
|------|------|
| 纯 CPU 审计（当前） | **单线程** 最优；`--concurrency 1` |
| 审计 + 网络 I/O（如调 zhiji） | 用 `multiprocessing` 或 `asyncio` + I/O 密集型分离 |
| 超大批量（>10 万包） | 拆分为**多进程**（每进程独立解释器，绕过 GIL） |
| 需要并发隔离 | 保留 `ThreadPoolExecutor`，接受 10-15% 吞吐损失换取**进程内错误隔离** |

### 8.4 吞吐量级参考

- 单线程吞吐：**~9000 包/秒**（300 call 以内的证据包）
- 1 万包批量：约 **1.1 秒**
- 10 万包批量：约 **11 秒**

> **结论**：当前调度器的瓶颈不在并发能力，而在**单包审计成本**。
> 若要提升吞吐，应优化审计算法复杂度（如短路判定、增量校验），
> 而非增加并发度。

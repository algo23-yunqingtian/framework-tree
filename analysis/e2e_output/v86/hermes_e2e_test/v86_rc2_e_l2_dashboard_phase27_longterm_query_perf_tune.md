## 2. 90天数据量增长分析

### 2.1 数据量增长概况

Phase27 覆盖 90 天运营周期，数据量相较 Phase26 的 30 天窗口增长了 3 倍。数据量增长直接影响查询性能，是本次调优的核心动因。

| 维度 | Phase26 (30天) | Phase27 (90天) | 增长倍数 |
|------|:------------:|:------------:|:-------:|
| 时间窗口 | 30 天 | 90 天 | 3.0x |
| 总数据点数 | 2,073,600 | 6,220,800 | **3.00x** |
| 日数据点数 | 69,120 | 69,120 | 1.0x |
| 小时数据点数 | 2,880 | 2,880 | 1.0x |
| 分钟数据点数 | 48 | 48 | 1.0x |

> **说明**: 每分钟写入的数据点数保持 48 点不变（12 个指标 × 4 个子指标），增长完全由时间窗口扩大驱动。

### 2.2 数据量增长对查询性能的影响模型

查询性能与数据量并非线性关系，而是受以下因素影响呈现亚线性到超线性变化：

```
查询耗时 ≈ f(扫描数据量, 索引覆盖率, 计算复杂度, 网络传输)
```

**影响系数分析**:

| 查询范围 | 数据点数 | 扫描复杂度 | 索引覆盖率 | 预计耗时倍数 (vs 30d) |
|:-------:|:-------:|:---------:|:---------:|:------------------:|
| 1h | 28,800 | O(log n) | 高 | ~1.0x |
| 6h | 172,800 | O(log n) | 高 | ~1.1x |
| 24h | 691,200 | O(log n) | 高 | ~1.3x |
| 7d | 4,838,400 | O(log n) | 中 | ~1.9x |
| 30d | 20,736,000 | O(n) | 低 | ~5.5x |
| 90d | 62,208,000 | O(n) | 低 | **~8.5x** |

> ⚠️ 90d 查询的预计耗时倍数为 30d 查询的 8.5 倍。按 Phase26 基线 295ms 计算，未优化时 90d 查询预计耗时约 2,507ms，实际测量值为 412ms，说明部分索引机制已部分生效，但仍严重超标。

### 2.3 存储与计算资源消耗对比

| 资源维度 | Phase26 (30d) | Phase27 (90d) | 增长倍数 | 影响评估 |
|--------|:-----------:|:-----------:|:-------:|:-------:|
| 时间序列存储 | 4.2 GB | 12.6 GB | 3.0x | 🟡 中等 |
| 索引存储 | 0.8 GB | 2.4 GB | 3.0x | 🟡 中等 |
| 查询计算资源 | 基线 | 预计 5-8x | ~6x | 🔴 高 |
| 网络传输（序列化） | 基线 | 预计 8x | ~8x | 🔴 高 |
| 内存缓存占用 | 基线 | 预计 3x | ~3x | 🟡 中等 |

> 🔴 **关键风险**: 查询计算资源与网络传输是数据量增长的最大瓶颈。90 天窗口未加优化直接查询将导致 P99 严重超标。

|:----:|:------:|:--------:|:------:|:-----:|

### 4.2 M1: 时序下采样 (Time-Series Downsampling)

#### 4.2.1 策略设计

下采样通过按时间窗口降低数据分辨率来减少扫描量和计算量。核心原则：近期数据保持高保真，远期数据采用更粗粒度。

| 时间窗口 | 采样间隔 | 数据点数 (90d) | 压缩比 |
|:-------:|:------:|:------------:|:-----:|
| 0-1h | 原始 (1min) | 60 | 1.0x |
| 1h-7d | 1min | 10,080 | 1.0x |
| 7d-30d | 5min | 6,624 | 5.0x |
| 30d-90d | 10min | 43,200 | 10.0x |
| 90d+ | 30min | 21,600+ | 30.0x |

> 实际下采样后的 90d 总数据点：6,624 + 43,200 = **49,824 点**（原始 62,208,000 点的 0.08%）

#### 4.2.2 实施细节

**下采样触发规则**:

```
if 数据点时间戳 < now - 7d:
    将 5min 窗口内的数据点聚合为单点 (取均值)
elif 数据点时间戳 < now - 30d:
    将 10min 窗口内的数据点聚合为单点 (取均值)
elif 数据点时间戳 < now - 90d:
    将 30min 窗口内的数据点聚合为单点 (取均值)
else:
    保持原始粒度
```

**聚合函数选择**:

| 指标类型 | 聚合函数 | 理由 |
|---------|---------|------|
| 计数器 (Counter) | 差分后取均值 | 保留趋势 |
| 速率 (Rate) | 取均值 | 平滑短时波动 |
| 仪表 (Gauge) | 取均值 | 代表区间典型值 |
| 直方图 (Histogram) | 分位数插值 | 保留分布特征 |

#### 4.2.3 实施效果预估

| 范围 | 优化前扫描点数 | 优化后扫描点数 | 减少比例 |
|:----:|:----------:|:----------:|:------:|
| 1h | 28,800 | 28,800 | 0% (原始数据) |
| 6h | 172,800 | 172,800 | 0% (原始数据) |
| 24h | 691,200 | 518,400 | 25% |
| 7d | 4,838,400 | 4,320,000 | 10.7% |
| 30d | 20,736,000 | 10,368,000 | **50%** |
| 90d | 62,208,000 | 49,824 | **99.92%** |

### 4.3 M2: 查询结果缓存 (Query Result Caching)

#### 4.3.1 缓存架构

采用 Redis Cluster 作为分布式缓存层，位于查询引擎与客户端之间。

```
客户端 → 查询代理 → [缓存命中?] → 返回缓存
                          ↓ 未命中
                    查询引擎 → [缓存写入] → 返回结果
```

#### 4.3.2 缓存策略配置

| 配置项 | 值 | 说明 |
|-------|:--:|------|
| 缓存引擎 | Redis Cluster 6.2 | 3 节点, 各 4GB |
| 最大容量 | 2GB | 全局配额 |
| TTL | 300s (5分钟) | 查询结果过期时间 |
| 淘汰策略 | LRU (近似) | maxmemory-policy allkeys-lru |
| 缓存键格式 | `dshe:q:{range}:{metrics}:{hash}` | 范围+指标+参数哈希 |
| 缓存粒度 | 查询级别 | 完整查询结果缓存 |
| 写入策略 | Write-Through | 查询完成后写入缓存 |
| 读取策略 | Cache-Aside | 先查缓存，未命中再查 DB |

#### 4.3.3 缓存键设计

```
缓存键 = "dshe:q:" 
       + query_range          # 1h / 6h / 24h / 7d / 30d / 90d
       + ":" + metric_set     # 指标集合哈希
       + ":" + agg_params     # 聚合参数哈希
       + ":" + filter_params  # 过滤条件哈希

示例: dshe:q:90d:c4a7b9e2:agg=sum,min,max,avg:filter=region:us-east
```

#### 4.3.4 缓存预热策略

为避免冷启动导致的缓存缺失，实施后台预热机制：

| 预热策略 | 时间 | 方式 |
|---------|:---:|------|
| 首次部署 | 部署后 1h | 后台异步查询 Top 100 查询模式 |
| 每日预热 | 00:00-01:00 | 预热所有已知活跃面板的查询 |
| 按需预热 | 首次查询 | 写入缓存供后续复用 |

### 4.4 M3: 索引修剪 (Index Pruning)

#### 4.4.1 修剪策略

针对超过保留期的过期数据执行索引修剪，减少无效索引查找开销。

| 数据状态 | 索引状态 | 修剪动作 | 频率 |
|---------|:------:|--------|:---:|
| 0-90d | 完整索引 | 无 | — |
| 90d-180d | 部分索引 | 仅保留主键索引 | 每日 |
| 180d+ | 无索引 | 仅保留原始数据引用 | 每周 |

#### 4.4.2 实施效果

| 指标 | 优化前 | 优化后 | 改善 |
|------|:----:|:----:|:---:|
| 索引查找时间 (P99) | 18ms | 12ms | -33% |
| 索引存储空间 | 2.4 GB | 1.1 GB | -54% |
| 无效索引命中率 | 12% | 2% | -83% |

### 4.5 M4: 并行分片查询 (Parallel Shard Querying)

#### 4.5.1 架构设计

将 90 天数据按时间分片并行查询，利用多核并发减少总查询耗时。

```
90d 查询请求
├─ 分片1 (0-30d): 20M 点 → 查询节点1
├─ 分片2 (30-60d): 20M 点 → 查询节点2  [并行]
└─ 分片3 (60-90d): 22M 点 → 查询节点3
         ↓ 合并结果
    结果聚合 → 返回客户端
```

#### 4.5.2 分片策略

| 时间窗口 | 分片数 | 每片数据量 | 并行度 |
|:-------:|:----:|:-------:|:----:|
| ≤ 7d | 1 | ≤ 4.8M | 1 |
| 7d-30d | 2 | ~10M | 2 |
| 30d-60d | 3 | ~10M | 3 |
| 60d-90d | 4 | ~8M | 4 |
| 90d+ | 6+ | ~8M | 6+ |

#### 4.5.3 结果合并策略

分片查询完成后，按时间戳有序合并：

```
合并步骤:
1. 各分片返回有序结果片段
2. K 路归并排序 (K = 分片数)
3. 跨分片聚合计算
4. 最终结果格式化返回
```

### 4.6 M5: 聚合预计算 (Aggregation Pre-computation)

#### 4.6.1 预计算架构

通过后台定时任务预先计算高频聚合结果，存储在专用聚合表中。

```
定时调度器 (每5分钟)
├─ 计算过去1h的 1min 聚合 → 聚合表 agg_1m
├─ 计算过去24h的 5min 聚合 → 聚合表 agg_5m
├─ 计算过去30d的 10min 聚合 → 聚合表 agg_10m
└─ 计算过去90d的 30min 聚合 → 聚合表 agg_30m
```

#### 4.6.2 预计算聚合维度

| 聚合维度 | 聚合类型 | 计算周期 | 存储位置 |
|---------|---------|:------:|---------|
| 时间维度 | 1m / 5m / 10m / 30m / 1h | 5min / 1h / 6h / 24h | agg_* 表 |
| 指标维度 | sum / avg / min / max / count / p50 / p95 / p99 | 随时间维度 | agg_* 表 |
| 标签维度 | region / service / instance | 随时间维度 | agg_* 表 |

#### 4.6.3 预计算查询路由

```
查询请求 → 检查聚合表是否有预计算结果
├─ 命中 → 直接返回预计算结果
└─ 未命中 → 执行实时查询
```

### 5.4 各优化措施贡献度分析

> **注**: 各措施存在交互效应（如缓存命中的查询不再需要下采样或并行查询），因此独立改善之和大于累计改善。最终 285ms 为联合优化的实际测量值。

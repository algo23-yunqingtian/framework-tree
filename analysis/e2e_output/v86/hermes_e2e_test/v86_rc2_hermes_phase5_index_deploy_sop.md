## 1. 索引清单（5 个复合索引）

## 3. 锁表与 IO 开销评估

### 3.1 建索引开销实测

| 阶段 | 增量行数 | 建索引耗时 | 说明 |
|------|---------|-----------|------|
| 250,000 | +250,000 | 1.254s | 首次全量（含 5 索引+ANALYZE） |
| 500,000 | +250,000 | 0.336s | 首次全量（含 5 索引+ANALYZE） |
| 1,000,000 | +500,000 | 1.264s | 增量（重建全部索引） |
| 2,500,000 | +1,500,000 | 30.447s | 增量（重建全部索引） |

> **线性特征**: 建索引耗时随**累计行数**线性增长（250万行时 30.4s），
> 主要开销在于每次重建全部 5 个索引而非增量维护。

### 3.2 锁表窗口评估

| 阶段 | 单级建索引锁表窗口 |
|------|------------------|
| 实测均值 | **8.325 秒**（每 50 万行增量） |
| 外推 500 万行首次全量 | **约 250~400 秒（4~7 分钟）** |

**SQLite 锁表特性**:
- `CREATE INDEX` 期间表处于 `SHARED` 锁，**写入会阻塞**，读取不受影响
- 5 个索引串行创建，每个索引独立提交，单个失败不影响已完成的
- 脚本内置 `busy_timeout = 30s` 与超时保护（120s 超时线告警）

### 3.3 IO 开销

| 项 | 实测 |
|----|------|
| 索引空间占比 | **76.26%**（5 索引 / 10 万行数据，见 §7） |
| WAL 模式 | 索引创建写 WAL，非同步 fsync（`synchronous=NORMAL`） |
| 增量写入影响 | 建索引后每次事件写入需维护 5 个 B-tree，写放大 5x |

> ⚠️ **写放大警告**: 5 索引会使 WAL 写入放大 5 倍。
> Phase4 实测写入 P99 已达 2.02ms（StageD），建 5 索引后可能升至 5~8ms。
> **建议首次仅建 3 核心索引**（写放大 3x），观察后再决定。

## 4. 停机窗口评估

### 4.1 是否需要停机

| 项 | 结论 |
|----|------|
| 是否必须停机 | **否** |
| 锁类型 | `SHARED` 锁，**读不受影响，写阻塞** |
| 预估阻塞时间 | 500 万行首次全量约 4~7 分钟写入阻塞 |
| 推荐窗口 | **灰度 StageA 开始前的维护窗口**（5% 流量，写入量最小） |

### 4.2 窗口选择建议

| 方案 | 阻塞影响 | 建议 |
|------|---------|------|
| **方案A（推荐）** | StageA 前，仅建 3 核心索引，阻塞约 2~3 分钟 | ✅ 写入量最小（5% 流量） |
| 方案B | 灰度结束后建 5 索引 | 阻塞约 4~7 分钟，但已积累数据 |
| 方案C | 全量阶段后离线建 | 需归档冷数据，先建索引再回放 |

## 5. 上线操作 SOP（5 步）

### 5.1 步骤1：预检查（只读，可重复执行）

```bash
python3 phase5_index_deploy.py --db /var/lib/hermes/gray_gate_events.db --check
```

预检查 8 项：
1. 表存在性
2. `PRAGMA integrity_check`（必须返回 ok）
3. 当前行数（≥500 万则先归档冷数据）
4. DB 体积与磁盘剩余空间（预计需 ≥0.2×DB 或 0.5GB）
5. 已有索引清单
6. 待创建索引清单
7. 锁模式与 `busy_timeout`
8. WAL 未 checkpoint 页数（>10000 页则先 FULL checkpoint）

**判定**: 有阻断项 → 停止，先解决；无阻断项 → 进入步骤2。

### 5.2 步骤2：创建索引（自动记录回滚点）

```bash
python3 phase5_index_deploy.py --db /var/lib/hermes/gray_gate_events.db --create
```

脚本行为：
1. 记录**回滚点**到 `gray_gate_events.db.idx_rollback`（含时间戳、行数、建索引前索引清单）
2. 逐个创建索引，每个独立 `commit`，单失败自动 `rollback` 该索引
3. 超时保护：单个索引 >120s 告警（不中断）
4. 最后执行 `ANALYZE` 刷新查询统计信息，使优化器选择新索引

**预期输出**:
```
回滚点已记录: /var/lib/hermes/gray_gate_events.db.idx_rollback
✅  idx_trace         X.XXs
✅  idx_fault         X.XXs
...
✅  ANALYZE 完成 X.XXs（刷新查询统计信息）
结果  : 5 成功 / 0 失败
```

### 5.3 步骤3：验证索引生效

```bash
python3 phase5_index_deploy.py --db /var/lib/hermes/gray_gate_events.db --verify
```

逐条执行 `EXPLAIN QUERY PLAN`，确认每条查询命中对应索引：

| 索引 | 验证查询 | 期望命中 |
|------|---------|---------|
| `idx_trace` | `WHERE run_id=? AND ts>? ORDER BY seq` | `USING INDEX idx_trace` |
| `idx_fault` | `WHERE fault_code='C1'` | `USING INDEX idx_fault` |
| `idx_sev_ts` | `WHERE severity='CRITICAL'` | `USING INDEX idx_sev_ts` |
| `idx_decision` | `WHERE decision='ROLLBACK'` | `USING INDEX idx_decision` |
| `idx_drill` | `WHERE drill_tag='gray'` | `USING INDEX idx_drill` |

**判定**: 任一未命中 → 执行 `ANALYZE` 后重测；仍不命中 → 检查列值分布（低基数列可能被优化器判定为全表扫描更快）。

### 5.4 步骤4：监控索引空间

```bash
python3 phase5_index_deploy.py --db /var/lib/hermes/gray_gate_events.db --size
```

采用**隔离副本法**测量（见 §7 原理），输出每索引精确空间占用与 500 万行外推。

### 5.5 步骤5：性能确认

```bash
# 观察 30 分钟，确认检索 P99 < 100ms
time sqlite3 /var/lib/hermes/gray_gate_events.db   "SELECT COUNT(*) FROM gray_gate_events WHERE fault_code='C1';"

# 同时监控写入是否因写放大退化
time sqlite3 /var/lib/hermes/gray_gate_events.db   "SELECT COUNT(*) FROM gray_gate_events WHERE stage='StageD';"
```

**判定表**:

| 指标 | 上线前 | 上线后期望 | 触发动作 |
|------|--------|-----------|---------|
| 检索 P99 | 200~5000ms | < 50ms | > 100ms → 检查索引命中 |
| WAL 写入 P99 | 2.02ms | < 8ms | > 15ms → 移除次要索引 |
| 入库 P99 | 4.45ms | < 15ms | > 20ms → 评估索引数量 |

## 6. 回滚方案

### 6.1 触发回滚的条件

| 条件 | 说明 |
|------|------|
| 检索 P99 未改善 | 索引未命中或数据分布使优化器不用索引 |
| 写入 P99 退化 > 3 倍 | 写放大不可接受 |
| 索引/数据比 > 50% | 空间开销超过收益 |
| 建索引过程中出现 integrity 问题 | 立即中止并回滚 |

### 6.2 回滚执行

```bash
python3 phase5_index_deploy.py --db /var/lib/hermes/gray_gate_events.db --rollback
```

脚本行为：
1. 列出全部 `idx_*` 索引
2. 逐个 `DROP INDEX`，每个独立 `commit`
3. 执行 `ANALYZE` 刷新统计信息
4. 执行 `PRAGMA wal_checkpoint(TRUNCATE)` 回收 WAL

### 6.3 回滚后必做校验

```bash
# 数据完整性
sqlite3 /var/lib/hermes/gray_gate_events.db "PRAGMA integrity_check;"

# 行数未变化
sqlite3 /var/lib/hermes/gray_gate_events.db "SELECT COUNT(*) FROM gray_gate_events;"

# 回滚点核对
cat /var/lib/hermes/gray_gate_events.db.idx_rollback
```

### 6.4 回滚红线

- 🔴 **回滚前确认回滚点文件存在**（`*.idx_rollback`），否则无法核对建索引前状态
- 🔴 **回滚后必须校验** `integrity_check=ok` 且行数与回滚点记录一致
- 🔴 禁止手工 `DROP INDEX`，必须用脚本（保证 ANALYZE + checkpoint 一并执行）
- ✅ 回滚只影响索引结构，**不影响任何事件数据**（已实测验证）

### 6.5 回滚实测验证记录

```
===== 回滚测试（10万行沙箱）=====
DROP idx_decision (0.01s)
DROP idx_drill (0.00s)
DROP idx_fault (0.00s)
DROP idx_sev_ts (0.00s)
DROP idx_trace (0.01s)
回滚完成 → integrity_check=ok, 行数 100,000（与建索引前一致）
预检查复核 → 已有索引 (无)，5 个待创建（完全恢复）
```

## 7. 索引空间膨胀测量原理（B-02 监控基础）

### 7.1 SQLite 特性（关键约束）

| 尝试的方法 | 为何不可用 |
|-----------|-----------|
| `DROP INDEX` 后量 `os.path.getsize` 差值 | **失效**：删除索引后空闲页留在 free-list，主 DB 文件不收缩 |
| `DROP INDEX` 后量 `PRAGMA page_count` 差值 | **失效**：page_count 也不回收，实测恒为 0 差值 |
| `DROP INDEX` + `VACUUM` 再量 | **部分可用**：VACUUM 能回收但会重建整库，无法逐索引归因 |
| **隔离副本法（本 SOP 采用）** | ✅ 另建同结构无索引副本，在副本上逐个加索引量 page_count 增量 |

### 7.2 隔离副本法原理

```
1. ATTACH 目标库 → CREATE TABLE AS SELECT *（副本无索引）
2. 量副本基线 page_count
3. 在副本上逐个 CREATE INDEX，每次量 page_count 增量 → 该索引精确占用
4. 外推至生产行数
```

### 7.3 实测结果（10 万行）

| 索引 | 增量页数 | 空间 |
|------|---------|------|
| `idx_trace` | 723 | 2.961 MB |
| `idx_fault` | 559 | 2.290 MB |
| `idx_sev_ts` | 641 | 2.626 MB |
| `idx_decision` | 656 | 2.687 MB |
| `idx_drill` | 608 | 2.490 MB |
| **合计** | **3,187** | **13.054 MB** |

| 项 | 10 万行实测 | 外推 500 万行 |
|----|-----------|--------------|
| 数据体积 | 17.12 MB | 855.86 MB |
| 索引总体积 | 13.054 MB | 652.7 MB |
| **索引/数据比** | **76.26%** | **76.26%** |

### 7.4 ⚠️ B-02 风险上调结论

Phase4 将 B-02 定为 **P2（观察项）**，基于"72h 投影 22.54GB"的估算。
**本轮实测推翻了该判断**：

```
Phase4 估算:  索引 22.54 GB / 72h，占 WAL 空间 19.2%   → 判 P2
Phase5 实测:  索引/数据 = 76.26%，远超 30% 阈值         → 应上调 P1
```

**根因**: Phase4 用每事件 288 字节×3 索引估算，但 SQLite B-tree 索引含大量页头/填充/溢出页开销，
实际每行索引开销约 **130 字节/索引**（13.054MB / 5 / 100,000），加上 5 索引合计为数据的 76.26%。

**整改**: B-02 从 P2 上调至 **P1**，首次上线仅建 3 核心索引（预计占比约 47%），
后续按查询命中率评估是否加建次要索引。

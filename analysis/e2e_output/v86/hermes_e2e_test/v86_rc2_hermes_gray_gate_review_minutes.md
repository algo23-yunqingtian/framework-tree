## 3. 事件存储 WAL 切换阈值（评审项 2）

### 3.1 变更内容

事件存储从 JSONL 直写升级到 SQLite WAL 模式，自动切换阈值 1 万事件。

### 3.2 实测数据支撑

| 规模 | WAL 退化 | JSONL 退化 | 说明 |
|------|---------|-----------|------|
| 5000 事件 | 1.21x | 5.07x | JSONL 快但恶化 |
| 20000 事件 | **1.11x** | **23.72x** | WAL 恒定，JSONL 崩塌 |
| 100000 事件（外推） | ~1.1x | ~200x+ | 交叉点约 3 万事件 |

### 3.3 阈值合理性

- **1 万事件**：JSONL 退化约 5x，开始明显；WAL 仍恒定；
- **3 万事件**：理论交叉点，JSONL 与 WAL 延迟相当；
- **10 万事件**：JSONL 崩塌（200x+），WAL 仍恒定。

选择 1 万是**保守策略**：在 JSONL 开始退化前切换，留 3x 安全余量。

### 3.4 三方确认

| 方 | 确认 | 备注 |
|----|------|------|
| DSHB | ✅ | 批量上报场景用 `ingest_batch` 批量事务 |
| DSHE | ✅ | 告警路由适配器已适配 WAL 存储 |
| HERMES | ✅ | WAL 存储验证完成，9 项自检 PASS |

### 3.5 ⚠️ 批量事务性能优化建议

WAL 逐条 commit 约 0.7ms/条（主要 fsync 开销）。批量事务可大幅改善：

```python
# 批量上报推荐用法
store = AutoSwitchStore(events_db_path)
store.ingest_batch(event_list)  # 一个事务一次 fsync
```

**三方同意**：批量上报场景强制使用 `ingest_batch`，逐条上报仅用于小批量（<100 条）。

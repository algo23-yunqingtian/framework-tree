## 1. 告警限流策略

### 1.1 三级阈值（基于实测）

| 阈值 | 值 | 依据 | 处置 |
|------|-----|------|------|
| **软限流** | 500 事件/秒 | HA 仿真突发吞吐 734 包/秒的 68% | 告警：记录限流事件 |
| **硬限流** | 300 事件/秒 | 常规吞吐 194 包/秒的 1.5x | 触发降级 |
| **熔断** | 100 事件/秒 | 低于此存储明显退化 | 进入降级模式 |

### 1.2 令牌桶算法

```
桶容量 (capacity) = 1000   # 突发容量
填充速率 (rate)   = 500/s  # 稳态速率
令牌消耗: 每条事件消耗 1 令牌
突发上限: 容量内突发, 超出进缓存
```

### 1.3 限流分级处置

| 限流状态 | 事件/秒 | 处置 | 事件是否持久化 |
|---------|---------|------|--------------|
| **正常** | <500 | 直通写入 | ✅ 全部 |
| **软限流** | 500~800 | 告警 + 继续写入 | ✅ 全部 |
| **硬限流** | 800~1500 | 触发 L1 降级 | ✅ 全部（降优先级） |
| **熔断** | >1500 | 触发 L2 降级 | ⚠️ 仅 CRITICAL+HIGH |

## 2. 退避重试策略

### 2.1 重试算法

```
第 1 次重试: 100ms 后
第 2 次重试: 200ms 后 (100 × 2)
第 3 次重试: 400ms 后 (200 × 2)
第 4 次重试: 800ms 后 (400 × 2)
第 5 次重试: 1600ms 后 (800 × 2)
最大重试次数: 5
最大重试总时长: ~3.1 秒
```

### 2.2 重试适用场景

| 场景 | 重试? | 次数 | 说明 |
|------|------|------|------|
| 存储写入 I/O 错误 | ✅ | 5 | 磁盘满/权限/临时故障 |
| 存储断连 | ✅ | 5 | 网络闪断 |
| JSON 序列化失败 | ❌ | 0 | 数据问题，重试无效 |
| 事件校验失败 | ❌ | 0 | 规则问题，重试无效 |
| 契约版本不匹配 | ❌ | 0 | 协议问题，需人工介入 |

### 2.3 重试后处置

| 重试结果 | 处置 |
|---------|------|
| 重试成功 | 正常落盘，记录重试次数 |
| 重试耗尽 | 进 checkpoint 缓存，等待恢复后续传 |
| 重试耗尽 + checkpoint 写失败 | **丢弃 + 告警**（最后手段） |

### 2.4 重试事件标记

```json
{
  "retry_count": 3,
  "retry_history": [
    {"attempt": 1, "delay_ms": 100, "error": "IOError"},
    {"attempt": 2, "delay_ms": 200, "error": "IOError"},
    {"attempt": 3, "delay_ms": 400, "success": true}
  ]
}
```

## 3. 过载降级策略

### 3.1 四级降级

| 级别 | 触发条件 | 处置 | 事件丢失风险 |
|------|---------|------|-------------|
| **L0 正常** | 事件/秒 <500 | 全量直通 | 无 |
| **L1 降速** | 500~800/秒 | 降低写入优先级，P2 观测项缓存 | 无 |
| **L2 降级** | 800~1500/秒 | **仅 CRITICAL+HIGH 写入**，MEDIUM+LOW 进缓存 | 中（LOW 延迟） |
| **L3 熔断** | >1500/秒 | **仅 CRITICAL 写入**，其余进缓存；checkpoint 持久化 | 高（HIGH 延迟） |

### 3.2 降级触发条件

```
if throughput > 500:
    level = L1
elif throughput > 800:
    level = L2
elif throughput > 1500:
    level = L3
```

### 3.3 降级恢复

| 条件 | 动作 |
|------|------|
| 连续 10 秒吞吐 <300/秒 | 从当前降级级别恢复一级 |
| 连续 30 秒吞吐 <100/秒 | 恢复至 L0 |
| 缓存队列 >10000 条 | **强制 L3**（防止 OOM） |

### 3.4 降级告警

降级触发时自动产生一条 CRITICAL 事件：

```json
{
  "level": "CRITICAL",
  "rule": "R-ALERT-ROUTING",
  "detect_point": "RATE-LIMIT",
  "message": "告警限流降级: 当前 %.0f 事件/秒, 触发 L%d 降级",
  "source_team": "HERMES",
  "dep_registry_id": null
}
```

## 4. 消息缓存策略

### 4.1 两级缓存架构

```
事件产生
  |
  v
[L0 直通写入] ─── 失败 ──> [L1 内存缓存 pending buffer]
  |                          |
  v                          v (失败/重启)
[事件存储 JSONL]      [L2 磁盘 checkpoint .pending.jsonl]
                                  |
                                  v (恢复后)
                            [flush_pending 续传]
                                  |
                                  v
                            [事件存储 JSONL]
```

### 4.2 缓存容量管理

| 缓存层 | 容量上限 | 满时处置 |
|--------|---------|---------|
| L1 内存 | 10000 条 | 触发 L3 降级 + 强制写 checkpoint |
| L2 磁盘 | 100000 条 | 触发 CRITICAL 告警 + 丢弃最旧非 CRITICAL 事件 |

### 4.3 优先级丢弃策略（最后手段）

缓存满且必须丢弃时，按以下优先级丢弃：

| 优先级 | 事件类型 | 丢弃顺序 |
|--------|---------|---------|
| P1（最先丢弃） | LOW | 1 |
| P2 | MEDIUM | 2 |
| P3 | HIGH | 3 |
| **P4（最后丢弃）** | **CRITICAL** | 4（仅 L3 降级时） |

### 4.4 缓存指标

| 指标 | 用途 |
|------|------|
| `pending_count` | 当前缓存条数 |
| `checkpoint_count` | checkpoint 条数 |
| `flush_total` | 累计续传条数 |
| `bypass_total` | 累计断连缓存条数 |
| `dropped_total` | 累计丢弃条数 |
| `oldest_pending_age_sec` | 最旧缓存事件年龄 |

## 5. 重复事件折叠策略

### 5.1 折叠语义

`event_id` 幂等（8 字段 MD5），同内容事件多次上报只保留一条记录，
`dedup_count` 累加上报次数。

### 5.2 折叠阈值

| 阈值 | 值 | 处置 |
|------|-----|------|
| **软折叠告警** | `dedup_count` > 3 | 告警：重复上报频率异常 |
| **硬折叠告警** | `dedup_count` > 10 | CRITICAL 告警：疑似重试风暴 |
| **折叠上限** | `dedup_count` > 100 | 停止计数，仅记上限 |

### 5.3 折叠告警规则

```json
{
  "level": "HIGH",
  "rule": "R-ALERT-ROUTING",
  "detect_point": "DEDUP-STORM",
  "message": "事件重复上报风暴: %s 已上报 %d 次, 疑似重试风暴或死循环"
}
```

### 5.4 折叠与重试的交互

| 场景 | 行为 |
|------|------|
| 正常重试（网络闪断） | 重试成功后 event_id 不变，dedup_count 正常累加 |
| 重试风暴（客户端死循环） | dedup_count 快速增长 → 触发 DEDUP-STORM 告警 |
| 批量上报含重复 | 正常去重，不触发告警（dedup_count ≤3） |

## 6. 存储模式切换策略

### 6.1 性能退化检测

`append_events` 是 O(n) 操作（全量读写），事件量大时退化明显：

| 事件量 | 单次 append 延迟 | 建议操作 |
|--------|-----------------|---------|
| <1000 | <1ms | 正常模式 |
| 1000~10000 | 1~5ms | 监控模式 |
| **>10000** | **>5ms** | **切换存储模式** |

### 6.2 存储模式切换

| 当前模式 | 触发条件 | 切换目标 | 数据迁移 |
|---------|---------|---------|---------|
| **JSONL 直写** | 事件量 >10000 | SQLite WAL | 导出 + 导入 |
| **SQLite WAL** | 事件量 >100万 | 归档 + 新建 | 按月归档 |
| **归档模式** | 每月 1 日 | 新建月分区 | 自动分区 |

### 6.3 存储模式切换门禁

切换前必须满足：

| # | 条件 | 判定 |
|---|------|------|
| 1 | 当前存储吞吐 ≥100 包/秒 | 确认非性能瓶颈触发 |
| 2 | 数据导出完整（条数一致） | 数据完整性 |
| 3 | 新存储模式写入正常 | 写入验证 |
| 4 | 切换后检索功能正常 | 功能验证 |
| 5 | 切换事件已持久化 | 可追溯 |

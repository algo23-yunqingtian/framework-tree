## 3. 缺陷详情

### DEFECT-001: Gate 大盘子面板批量渲染超时

| 字段 | 值 |
|------|-----|
| **缺陷 ID** | DEFECT-001 |
| **优化项** | #3 面板渲染性能优化 |
| **子任务** | #3-T02（子面板按需渲染框架） |
| **严重程度** | P2（非阻塞） |
| **类别** | Performance（性能） |
| **发现方式** | UT 自测（GATE-DSHE-017） |
| **测试环境** | Shadow, 50 并发用户, 本地 Mock API |
| **发现日期** | 2026-10-04 |
| **发现人** | UT 自动化测试框架 |
| **关联用例** | GATE-DSHE-017（子面板渲染性能） |

#### 缺陷描述

Gate 大盘子面板批量渲染在 50 并发用户条件下偶发超过 3.0s 阈值。测量 P99 = 3.1s（100 次测试运行中 1 次触发），超出 3.0s 目标阈值。

**详细场景**：
- Gate 大盘共 56 个子面板（5 个分组），按分组依次加载
- 批量渲染分 4 批执行，每批 14 个面板，批间间隔 16ms（1 帧）
- 50 并发用户同时触发 Gate 大盘加载时，第 3 批（面板 29-42）出现超时
- 超时触发保护机制（2s timeout protection），后续面板被延迟加载

#### 根因分析

```
根因链：
  50 并发用户同时触发渲染
  → 主线程请求队列饱和
  → 16ms 批间间隔不足以让出渲染时间
  → 第 3 批面板（29-42）渲染耗时延长
  → 单批耗时超过 2s timeout protection 阈值
  → 整体 P99 从预期 2.5s 升至 3.1s
```

**技术细节**：
1. **批间间隔不足**：16ms（约 1 帧）在正常负载下足够，但 50 并发时主线程被大量 DOM 操作占满，16ms 无法保证浏览器完成布局/绘制
2. **批次大小固定**：14 个面板/批 未根据并发量自适应调整，高并发下每批处理量过大
3. **主线程争用**：50 个用户会话的渲染任务竞争同一主线程，导致单批实际执行时间远超预期

#### 影响评估

| 维度 | 评估 |
|------|------|
| **触发概率** | 100 次运行中 1 次（1%），仅在高并发下出现 |
| **数据完整性** | 无数据丢失，无渲染错误 |
| **用户可见影响** | 超时保护正常触发，无用户可见的渲染失败 |
| **业务影响** | 极低 — 仅延迟部分面板显示，非阻塞性降级 |
| **SLA 影响** | P99 3.1s vs 目标 3.0s，偏差 0.1s（3.3%） |

#### 修复方案

**方案 A（采纳）**：增大批间间隔 + 自适应批次大小

1. **批间间隔**：`batchScheduler.batchInterval` 从 16ms 调整为 32ms
2. **自适应批次大小**：新增 `adaptiveBatchSize()` 函数
   - 并发用户 ≤ 20：批次大小 14（原值）
   - 并发用户 20-50：批次大小 10
   - 并发用户 > 50：批次大小 8
3. **批间延迟递增**：第 N 批批间延迟 = `32ms × (1 + N × 0.1)`，给主线程更多喘息空间

**方案 B（未采纳）**：Web Worker 渲染分离
- 评估：架构改动过大，RC2 范围内不可行

**方案 C（未采纳）**：虚拟滚动
- 评估：仅适用于连续列表，Gate 大盘为分组布局，不适用

#### 修复代码变更

```javascript
// batchScheduler.js — 变更摘要
// 1. 批间间隔调整
batchScheduler.batchInterval = 32; // was: 16

// 2. 新增自适应批次大小函数
function adaptiveBatchSize(concurrentUsers) {
  if (concurrentUsers > 50) return 8;
  if (concurrentUsers > 20) return 10;
  return 14; // default
}

// 3. 批间延迟递增逻辑
function getBatchDelay(batchIndex) {
  return 32 * (1 + batchIndex * 0.1); // ms
}
```

### DEFECT-002: 硅产业门户进度条更新间隔超标

| 字段 | 值 |
|------|-----|
| **缺陷 ID** | DEFECT-002 |
| **优化项** | #10 硅产业数据批量加载 |
| **子任务** | #3-T05（硅产业门户进度条 UX 反馈）— 共享自 #3 |
| **严重程度** | P2（非阻塞） |
| **类别** | UX/Performance（体验/性能） |
| **发现方式** | UT 自测（GATE-DSHE-010） |
| **测试环境** | Shadow, 本地 Mock API, 顺序加载 |
| **发现日期** | 2026-10-04 |
| **发现人** | UT 自动化测试框架 |
| **关联用例** | GATE-DSHE-010（批量加载性能） |

#### 缺陷描述

硅产业门户进度条更新间隔在第 3 批（非核心维度）加载时超过 200ms 阈值。实测间隔：245ms（最差情况），超出 ≤200ms 目标阈值。

**详细场景**：
- 硅产业门户按 5 个批次加载数据（每批约 15s 间隔）
- 每批包含 5 个维度 × 12 个数据点
- 进度条更新依赖 `setTimeout` 回调链
- 第 3 批数据量较大（5 维度 × 12 点），`setData` 回调处理时间过长
- 进度条更新间隔从预期的 100-150ms 延长至 245ms

#### 根因分析

```
根因链：
  第 3 批数据量较大（5 维度 × 12 数据点）
  → setData 回调处理耗时增加
  → setTimeout 回调队列中的进度更新被延迟
  → 进度条更新间隔从 150ms 延长至 245ms
  → 超出 200ms 阈值 45ms（22.5% 偏差）
```

**技术细节**：
1. **无帧率节流**：进度条更新直接使用 `setTimeout`，未绑定 `requestAnimationFrame`
2. **数据量不均**：第 3 批数据量是其他批次的 1.4 倍，但未做预分配
3. **无帧预算检查**：未检查当前帧剩余时间预算，导致更新阻塞其他渲染任务

#### 影响评估

| 维度 | 评估 |
|------|------|
| **触发条件** | 仅在数据量较大时出现（第 3 批），非必现 |
| **功能影响** | 无 — 进度条最终正确更新，数据加载不受影响 |
| **视觉影响** | 进度条出现轻微卡顿/跳帧，用户可感知 |
| **数据完整性** | 无数据丢失，无渲染错误 |
| **SLA 影响** | 245ms vs 200ms 目标，偏差 22.5%，仅视觉层 |

#### 修复方案

**方案（采纳）**：`requestAnimationFrame` 节流 + 帧预算检查

1. **rAF 节流**：将所有进度条更新回调从 `setTimeout` 迁移至 `requestAnimationFrame`
2. **帧预算检查**：新增 `frameBudgetCheck()` 函数
   - 检查当前帧剩余预算（基于 `performance.now()` 与帧开始时间）
   - 剩余预算 < 20ms 时，将进度更新推迟到下一帧
3. **进度插值**：在帧间隙使用线性插值平滑进度条动画，消除视觉跳变

**方案 B（未采纳）**：预分配进度
- 评估：预分配进度条位置与真实加载进度可能不一致，增加复杂度

**方案 C（未采纳）**：Web Worker 数据解析
- 评估：进度条更新涉及 DOM 操作，无法在 Worker 中执行

#### 修复代码变更

```javascript
// progressBar.js — 变更摘要
// 1. 替换 setTimeout 为 rAF 节流
function updateProgress(percent) {
  requestAnimationFrame(() => {
    if (frameBudgetCheck()) {
      progressBar.style.width = `${percent}%`;
    } else {
      // 帧预算不足，推迟到下一帧
      pendingUpdate = percent;
      requestAnimationFrame(() => updateProgress(pendingUpdate));
    }
  });
}

// 2. 新增帧预算检查函数
function frameBudgetCheck() {
  const now = performance.now();
  const frameStart = lastFrameStart || now - 16;
  const elapsed = now - frameStart;
  return (16 - elapsed) > 20; // 剩余预算 > 20ms 才更新
}

// 3. 进度插值平滑
function interpolateProgress(from, to, duration) {
  const startTime = performance.now();
  function step() {
    const elapsed = performance.now() - startTime;
    const progress = Math.min(elapsed / duration, 1);
    const current = from + (to - from) * easeOutCubic(progress);
    updateProgress(current);
    if (progress < 1) requestAnimationFrame(step);
  }
  requestAnimationFrame(step);
}
```

### DEFECT-003: 降级恢复时间预测误差超标

| 字段 | 值 |
|------|-----|
| **缺陷 ID** | DEFECT-003 |
| **优化项** | #12 降级图表恢复提示 |
| **子任务** | #12-T01（降级恢复时间预测模型） |
| **严重程度** | P2（非阻塞） |
| **类别** | Logic/Accuracy（逻辑/精度） |
| **发现方式** | UT 自测（GATE-DSHE-046） |
| **测试环境** | Shadow, 7 张降级图表, 本地 Mock API（可配置恢复时间） |
| **发现日期** | 2026-10-04 |
| **发现人** | UT 自动化测试框架 |
| **关联用例** | GATE-DSHE-046（降级恢复时间提示） |

#### 缺陷描述

降级恢复时间预测模型对第 5 号图表（电解铝企业利润分布，L3 级降级）的预测误差达到 35%，超出 ≤30% 的阈值要求。预测值 "2h 15min" vs 实际值 "3h 45min"。

**详细场景**：
- 测试环境配置 7 张降级图表，涵盖 L1-L4 四级降级
- 第 5 号图表（电解铝企业利润分布）为 L3 级降级
- 该图表近期恢复模式异常：连续 3 次快速恢复（<30min）后出现长时间中断（>2h）
- 预测模型输出 "2h 15min"，实际恢复耗时 "3h 45min"
- 误差率 = |2h15min - 3h45min| / 3h45min ≈ 35%

#### 根因分析

```
根因链：
  第 5 号图表恢复模式异常（连续快速恢复 → 长时间中断）
  → 简单指数移动平均（EMA）模型对近期数据赋予过高权重
  → 近期 3 次快速恢复（<30min）主导了预测权重
  → 模型低估了长时间中断的可能性
  → 预测值 2h15min 远低于实际值 3h45min
  → 误差率 35%，超出 30% 阈值
```

**技术细节**：
1. **EMA 权重偏差**：简单 EMA 使用固定衰减因子（α=0.3），对近期数据过度敏感
2. **模式检测缺失**：未检测恢复间隔的方差变化，无法识别异常模式
3. **记忆窗口过短**：仅使用 7 天历史数据，长时间中断模式被快速恢复模式覆盖
4. **无最小预测值**：L3 级降级图表未设置最低预测恢复时间

#### 影响评估

| 维度 | 评估 |
|------|------|
| **触发概率** | 7 张图表中 1 张（14.3%），仅特定恢复模式下出现 |
| **功能影响** | 用户可能被误导关于恢复时间，但图表仍正常降级/恢复 |
| **数据完整性** | 无数据丢失，无渲染错误 |
| **业务影响** | 中等 — 用户可能做出错误的操作时机判断 |
| **SLA 影响** | 35% vs 30% 阈值，偏差 5 个百分点 |

#### 修复方案

**方案（采纳）**：加权历史数据 + 模式检测 + 最小预测值

1. **加权 EMA（WEMA）**：引入更长记忆窗口（30 天 vs 原 7 天），按时间衰减加权
   - 30 天内数据按指数衰减加权，衰减因子 α 从 0.3 调整为 0.15
   - 长时间中断（>2h）赋予 2x 权重，避免被短期快速恢复覆盖
2. **方差模式检测**：新增 `variancePatternDetect()` 函数
   - 计算恢复间隔方差
   - 方差 > 2σ 时，增大预测不确定度范围（显示区间而非单点值）
3. **最小预测值保护**：L3 级降级图表且历史存在长时间中断（>2h）时，设置最小预测值 2h
   - 防止模型输出过短的恢复时间
4. **多模型集成**：EMA 预测值与线性回归预测值取加权平均（EMA 0.6, LR 0.4）

**方案 B（未采纳）**：完全替换为 LSTM 预测模型
- 评估：模型复杂度高，训练数据不足，RC2 范围内不可行

// degradationPredictor.js — 变更摘要
// 1. 加权 EMA 替换简单 EMA
function weightedEMA(history, windowDays = 30) {
  const sorted = history.sort((a, b) => a.timestamp - b.timestamp);
  const cutoff = Date.now() - windowDays * 86400000;
  const valid = sorted.filter(h => h.timestamp >= cutoff);
  
  let weightedSum = 0, totalWeight = 0;
  valid.forEach((h, i) => {
    const age = (Date.now() - h.timestamp) / 86400000;
    const baseWeight = Math.exp(-0.15 * age); // 衰减因子 0.15
    const outlierWeight = h.recoveryTime > 7200 ? 2.0 : 1.0; // 长时间中断 2x 权重
    const w = baseWeight * outlierWeight;
    weightedSum += h.recoveryTime * w;
    totalWeight += w;
  });
  return totalWeight > 0 ? weightedSum / totalWeight : defaultEstimate;
}

// 2. 新增方差模式检测
function variancePatternDetect(history) {
  const intervals = history.map(h => h.recoveryTime);
  const mean = intervals.reduce((a, b) => a + b, 0) / intervals.length;
  const variance = intervals.reduce((a, b) => a + Math.pow(b - mean, 2), 0) / intervals.length;
  const stdDev = Math.sqrt(variance);
  
  if (stdDev > 2 * mean) {
    return { 
      isHighVariance: true, 
      predictionRange: [mean - stdDev, mean + stdDev],
      uncertaintyLabel: '恢复时间不确定，可能大幅波动'
    };
  }
  return { isHighVariance: false, predictionRange: [mean * 0.8, mean * 1.2] };
}

// 3. L3 最小预测值保护
function applyMinimumGuard(prediction, degradationLevel, history) {
  if (degradationLevel === 'L3') {
    const hasProlongedOutage = history.some(h => h.recoveryTime > 7200);
    if (hasProlongedOutage && prediction < 7200) {
      return Math.max(prediction, 7200); // 最小 2h
    }
  }
  return prediction;
}

// 4. 多模型集成
function ensemblePredict(history, level) {
  const emaPred = weightedEMA(history);
  const lrPred = linearRegressionPredict(history);
  const ensemble = 0.6 * emaPred + 0.4 * lrPred;
  return applyMinimumGuard(ensemble, level, history);
}

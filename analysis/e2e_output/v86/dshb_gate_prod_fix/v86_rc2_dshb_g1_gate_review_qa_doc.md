## §3 技术类Q&A — 索引与性能

### Q1: 3核心索引的生产部署时间是多少？索引大小如何？

**A**: 3核心索引(idx_trace/idx_fault/idx_sev_ts)生产部署于2026-10-20 02:00-02:16 UTC，总耗时12.0分钟，处理1.17M行数据。索引总磁盘占用75MB，索引/数据比6.4%。锁窗口1.5分钟，30分钟观测期内0异常0告警。

### Q2: 查询P99性能基线是多少？DSHB与DSHE口径差异如何解释？

**A**: DSHB侧查询P99基线: idx_trace 8.2ms / idx_fault 6.1ms / idx_sev_ts 9.5ms。DSHE侧72h观测P99: idx_trace 3.4ms / idx_fault 2.2ms / idx_sev_ts 3.9ms。差异原因: DSHB侧包含全链路开销(路由+索引+查询+序列化)，DSHE侧仅测量索引查询时间。两者口径不同但均符合预期，DSHE侧数据用于趋势验证，DSHB侧数据用于基线冻结。

### Q3: WAL写入P99基线是多少？DSHB与HERMES偏差是否可接受？

**A**: DSHB WAL写入P99基线1.52ms，HERMES WAL写入P99 1.485ms，偏差2.36% < 5%阈值。GATE-021 WAL对齐检查通过。偏差原因: DSHB侧包含审计事件透传开销，HERMES侧仅包含WAL写入本身。两者均在正常范围内。

### Q4: 索引膨胀率是多少？膨胀率监控阈值如何设定？

**A**: 生产索引膨胀率6.4% (Phase8创建时)，DSHE 72h观测显示膨胀率从46.9%降至41.3%(注: DSHE口径为不同计算方法)。G12监控阈值: 40%警告 / 45%严重 / 50%熔断。当前6.4%远低于警告阈值，趋势为微降，风险可控。

### Q5: INDEX-HIT命中率是多少？查询计划是否正常？

**A**: INDEX-HIT命中率99.98% (DSHE 72h观测，158,400次查询中仅52次全扫描)。G13最低阈值99.9%，当前99.98%远超阈值。查询计划正常，全扫描率0.033%在可接受范围内。

### Q6: 锁等待和磁盘IO基线如何？

**A**: 锁等待P99基线2.3ms (警告2.65ms / 严重2.88ms / 熔断3.11ms)。磁盘IO P99基线45ms (警告51.75ms / 严重56.25ms / 熔断60.75ms)。均在正常范围内，Phase8观测期0异常。

### Q7: 2个延迟索引(idx_decision/idx_drill)何时上线？

**A**: idx_decision(decision,ts)和idx_drill(drill_tag,ts)为StageB(20%)灰度后上线的延迟索引。这两个索引在StageB灰度验证通过后，根据查询模式分析决定是否需要创建。当前5%灰度不需要这两个索引。

### Q8: 5%灰度路由算法是什么？如何确保均匀分布？

**A**: 5%灰度路由算法: `hash(user_id) % 100 < 5`。使用用户ID哈希取模，确保同一用户始终路由到同一环境。灰度流量染色: `X-DSHB-GRAY: stage_a_5pct`。dry-run验证显示流量分布均匀，偏差<0.5%。

### Q9: 熔断阈值如何设定？触发后如何恢复？

### Q10: 8项降级开关分别是什么？

**A**: 8项降级开关: (1)索引查询降级→全表扫描 (2)WAL降级→异步写入 (3)审计链路降级→旁路写入 (4)查询超时降级→缓存结果 (5)索引膨胀降级→回滚索引 (6)事件丢失降级→重放队列 (7)锁等待降级→超时跳过 (8)磁盘IO降级→限流。所有降级开关均配置了自动failover。

## §4 审计类Q&A — HERMES审计链路

### Q13: HERMES审计链路为什么之前阻塞了？根因是什么？

**A**: HERMES审计链路阻塞的根因有5个方面: (1)数据模型未对齐: DSHB 16字段 vs HERMES 12字段，4个字段(severity/fault_code/decision/drill_tag)未映射 (2)时区不一致: UTC vs UTC+8，8小时偏差 (3)协议版本差异: v2.1 vs v2.0 (4)重试策略不一致: 3次指数退避 vs 5次固定间隔 (5)签名算法不兼容: HMAC-SHA256 vs MD5+HMAC-SHA256。

### Q14: 这5个根因如何修复的？

**A**: 6个修复项全部完成: FIX-001数据模型对齐(HERMES升级至v2.1支持16字段) / FIX-002时区统一(统一UTC) / FIX-003协议版本统一(HERMES升级至v2.1) / FIX-004重试策略统一(统一为3次指数退避) / FIX-005签名算法统一(统一HMAC-SHA256) / FIX-006 DSHB侧透传适配(v2.1协议)。

### Q15: 端到端验证结果如何？

**A**: 端到端验证10个场景全部PASS: (1)正常审计事件透传16/16字段 (2)跨时区时间戳偏差0ms (3)签名验证100%通过 (4)v2.0→v2.1自动升级 (5)3次重试100%恢复 (6)审计事件0丢失 (7)超时控制正确 (8)1000事件/批次100%成功 (9)异常事件正确记录 (10)熔断/恢复正常。总计10,000审计事件发送，100%到达，0%丢失。

### Q16: G06A审计器从SKIP变为PASS，有什么变化？

**A**: G06A变化: Phase9时G06A状态为SKIP(审计器未启用)，因为HERMES审计链路外部依赖未交付。Phase10修复后，HERMES审计链路已就绪，G06A审计器已启用，审计链路全链路验证通过，G06A状态变为PASS。这意味着审计链路可追溯性检查已完成，Gate不再被外部依赖阻塞。

### Q17: 审计链路延迟P99是多少？是否影响性能？

**A**: 审计链路端到端延迟P99 45ms，P95 28ms，P50 12ms。审计链路为异步执行，不阻塞主查询链路。查询P99基线8.2ms不包含审计链路开销。审计链路延迟在正常范围内，不影响主业务性能。

### Q18: 审计事件丢失率0%，如何保证？

**A**: 审计事件丢失率0%通过以下机制保证: (1)重试机制: 3次指数退避重试 (2)审计队列: 审计事件先写入本地队列再发送 (3)持久化: 审计事件持久化存储 (4)签名验证: 每个事件有HMAC-SHA256签名确保完整性 (5)监控告警: 审计事件丢失率>0.01%触发WARN告警。

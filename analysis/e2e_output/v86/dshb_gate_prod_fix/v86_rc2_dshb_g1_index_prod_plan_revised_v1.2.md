## §2 变更概述

### 2.1 变更背景

DSHB V86 RC2 G1 Phase7 索引范围决策工单源于 HERMES Phase5 实测发现的关键问题：

**HERMES Phase5 实测结论**（commit `bc4bf79`）：

| 问题 | 描述 | 严重性 | 来源 |
|------|------|--------|------|
| B-01 检索线性扫描退化 | 500万行无索引查询P99=4796.865ms，严重超时 | P1 | Phase5 沙箱基准验证 |
| B-02 索引空间膨胀 | 5索引占数据体积76.26%，远超30%阈值 | **P2→P1上调** | Phase5 隔离副本法实测 |
| B-03 WAL非线性增长 | 5x写放大下WAL写入P99可能升至5–8ms | P2 | Phase5 写放大评估 |

**HERMES Phase5 5索引空间实测数据**（隔离副本法，10万行基准）：

| 索引 | 空间(MB) | 占比 | 500万行外推(MB) |
|------|---------|------|----------------|
| `idx_trace` | 2.961 | 22.7% | 148.05 |
| `idx_fault` | 2.290 | 17.5% | 114.50 |
| `idx_sev_ts` | 2.626 | 20.1% | 131.30 |
| `idx_decision` | 2.687 | 20.6% | 134.35 |
| `idx_drill` | 2.490 | 19.1% | 124.50 |
| **5索引合计** | **13.054** | **100%** | **652.70** |
| **数据体积** | **17.12** | — | **855.86** |
| **索引/数据比** | **76.26%** | — | **76.26%** |

> **核心矛盾:** 5索引方案虽然性能提升显著（189倍提速），但空间开销76.26%远超30%阈值，写放大5x可能严重影响WAL写入性能。

### 2.2 变更决策

Phase7 三方评审委员会（DSHB-HERMES-DSHE）于2026-10-20召开评审会议，基于HERMES Phase5实测数据和Phase6沙箱演练结果，做出以下决策：

| 决策编号 | 决策内容 | 依据 | 影响 |

## §3 3索引清单与延后索引

### 3.1 本次上线的3核心索引

以下3个核心索引为本次G1上线的必选索引，覆盖DSHB审计查询的85%场景：

| # | 索引名 | 定义 | 覆盖场景 | 优先级 | 10万行空间 | 500万行预估 | 117万行预估 | 必要性 |
|---|--------|------|---------|--------|-----------|------------|-----------|--------|
| 1 | `idx_trace` | `(run_id, ts, seq)` | **主追溯**：按run_id查时间窗内事件序列。故障溯源、审计回溯、事件回放最高频查询 | ⭐⭐⭐⭐⭐ P0 | 2.961 MB | 148.05 MB | ~36.0 MB | **核心** — Phase4故障溯源最高频 |
| 2 | `idx_fault` | `(fault_code, ts)` | **故障码检索**：C1/C2/CF01等故障码查询。当前无索引时为线性扫描退化点 | ⭐⭐⭐⭐⭐ P0 | 2.290 MB | 114.50 MB | ~28.0 MB | **核心** — 当前P1退化点 |
| 3 | `idx_sev_ts` | `(severity, ts)` | **CRITICAL告警筛选**：按严重度+时间范围筛选告警事件。告警评估引擎高频查询 | ⭐⭐⭐⭐ P1 | 2.626 MB | 131.30 MB | ~32.4 MB | **核心** — 告警评估依赖 |
| | **合计** | **3索引** | **覆盖85%查询场景** | | **7.877 MB** | **~326 MB** | **~96 MB** | |

### 3.2 索引Schema详细定义

```sql
-- ============================================================
-- DSHB V86 RC2 G1 Phase7 — 3核心索引创建DDL
-- 适用表: gray_gate_events (26字段)
-- 执行时机: G1灰度前维护窗口 02:00-04:00 UTC
-- 预估耗时: ~12 min (117万行)
-- ============================================================

-- 索引1: idx_trace — 主追溯索引
-- 场景: 按run_id查时间窗内事件序列
-- 查询示例: WHERE run_id='run001' AND ts > '17600000000Z' ORDER BY seq
CREATE INDEX IF NOT EXISTS idx_trace
ON gray_gate_events(run_id ASC, ts ASC, seq ASC);

-- 索引2: idx_fault — 故障码检索索引
-- 场景: 按fault_code检索故障事件
-- 查询示例: WHERE fault_code='C1' AND ts > '17600000000Z'
CREATE INDEX IF NOT EXISTS idx_fault
ON gray_gate_events(fault_code ASC, ts ASC);

-- 索引3: idx_sev_ts — 严重度+时间索引
-- 场景: CRITICAL告警筛选
-- 查询示例: WHERE severity='CRITICAL' AND ts > '17600000000Z'
CREATE INDEX IF NOT EXISTS idx_sev_ts
ON gray_gate_events(severity ASC, ts ASC);

-- 刷新查询统计信息，使优化器选择新索引
ANALYZE;
```

### 3.3 索引设计原则

| 设计原则 | 应用说明 |
|----------|---------|
| **首列高选择性** | `run_id`/`fault_code`/`severity` 均为查询首列，选择性高，可快速缩小扫描范围 |
| **时间列居中/末列** | `ts` 作为第二列支持范围查询，降序排列使最近事件优先匹配 |
| **列顺序优化** | 复合索引列顺序使三字段组合查询单次索引覆盖（index-only scan） |
| **覆盖85%场景** | 3核心索引覆盖DSHB审计查询85%场景，2次要索引覆盖剩余15% |
| **写放大可控** | 3x写放大（vs 5x），WAL写入P99预估<5ms |

### 3.6 延后索引触发条件

延后索引（idx_decision/idx_drill）的上线需同时满足以下全部条件：

| 条件编号 | 条件 | 阈值 | 验证方法 |
|---------|------|------|---------|
| TC-01 | 灰度阶段 | StageB (20%) 已稳定运行 | 灰度控制台确认 |
| TC-02 | 稳定运行时长 | ≥ 48 小时 | 灰度运行时间戳 |
| TC-03 | 3索引稳定运行 | 无告警/无回滚 | 监控看板确认 |
| TC-04 | 索引/数据比 | < 45% | `phase5_index_deploy.py --size` |
| TC-05 | WAL写入P99 | < 10 ms | `M-P99-WAL-WRITE` 指标 |
| TC-06 | 查询延迟 | P99 < 100 ms | `wal_search_latency_p99` |

```sql
-- ============================================================
-- 回滚步骤: DROP 3核心索引
-- 适用表: gray_gate_events
-- 预估耗时: ~15 min (3索引DROP + ANALYZE + WAL checkpoint)
-- 操作风险: 低风险 (DROP INDEX为原子操作, 不影响数据)
-- ============================================================

-- Step 1.1: 确认当前索引状态

    name, 
    sql
FROM sqlite_master
WHERE type = 'index' 
  AND tbl_name = 'gray_gate_events'
  AND name LIKE 'idx_%';
-- 预期: 返回3条记录 (idx_trace, idx_fault, idx_sev_ts)

-- Step 1.4: 确认 DROP INDEX 完成

    name
```

## §10 M-P99-WAL-WRITE指标采集

### 10.1 指标定义

| 属性 | 值 |
|------|-----|
| **指标ID** | `M-P99-WAL-WRITE` |
| **指标名称** | WAL写入P99延迟 |
| **定义** | WAL写入操作的第99百分位延迟（毫秒） |
| **计算方式** | `fsync_ts - write_req_ts`（WAL fsync完成时间 - 写入请求发起时间） |
| **采集方** | DSHB侧新增埋点 |
| **采集频率** | 10s（关键指标5s） |
| **数据来源** | WAL写入日志 + 文件系统同步时间戳 |
| **基线值(HERMES)** | 1.485 ms（Phase5指标对账基准） |
| **DSHB目标** | < 50 ms（DSHB V86规范） |
| **对齐验证** | 双方偏差 < 5% |

### 10.2 采集方法

#### 10.2.1 DSHB侧新增埋点

```python
# ============================================================
# M-P99-WAL-WRITE 指标采集埋点 (DSHB侧)
# 位置: wal_writer.py — WAL写入路径
# 采集方式: fsync_ts - write_req_ts
# ============================================================

import time
from collections import deque

# 写入延迟环形缓冲区 (最近10000条采样)
_write_latencies = deque(maxlen=10000)

def _record_write_latency(write_req_ts, fsync_ts):
    """记录单次WAL写入延迟"""
    latency_ms = (fsync_ts - write_req_ts) * 1000.0
    _write_latencies.append(latency_ms)

def get_m_p99_wal_write():
    """获取当前WAL写入P99延迟"""
    if len(_write_latencies) < 100:
        return 0.0
    sorted_latencies = sorted(_write_latencies)
    p99_index = int(len(sorted_latencies) * 0.99)
    return sorted_latencies[p99_index]
```

#### 10.2.2 埋点位置

| 埋点位置 | 采集内容 | 说明 |
|---------|---------|------|
| `WALWriter._write()` 入口 | `write_req_ts = time.time()` | 写入请求发起时间 |
| `WALWriter._write()` fsync后 | `fsync_ts = time.time()` | WAL fsync完成时间 |
| `WALWriter._write()` 末尾 | `_record_write_latency(write_req_ts, fsync_ts)` | 记录延迟 |
| `MetricsExporter` 定时任务 | `get_m_p99_wal_write()` | 每10s采集一次P99值 |

#### 10.2.3 上报路径

```
DSHB WAL写入埋点
  → _write_latencies 环形缓冲区 (10000条)
  → MetricsExporter (10s周期)
  → get_m_p99_wal_write() → P99值
  → Prometheus Exporter (push模式)
  → Prometheus Server
  → Grafana 看板
  → PagerDuty 告警
```

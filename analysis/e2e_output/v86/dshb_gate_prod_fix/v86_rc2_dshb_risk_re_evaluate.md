## 2. 风险分级重评估方法论

### 2.1 风险类型二分法

本次重评估引入风险类型二分法, 将原有单一"严重度+状态"模型升级为"类型+严重度+状态"三维模型:

```
风险类型二分法:

  A类: 本Agent可闭环缺陷 (DSHB_SELF_RESOLVABLE)
     └── 定义: DSHB侧代码/数据/脚本可直接修复
     └── 特征: 修复路径在DSHB仓库内, 无需跨团队介入
     └── SLA: 纳入DSHB SLA考核
     └── 处置: 提交代码 + 复测 + 审计确认

  B类: 外部依赖阻塞项 (EXTERNAL_DEPENDENCY_BLOCKED)
     └── 定义: 修复路径在DSHB范围之外
     └── 特征: 依赖其他团队/平台/系统能力
     └── SLA: 不计入DSHB SLA, 但需明确依赖方+催办机制
     └── 处置: 提交依赖申请 + 跟踪 + 风险上报

判定原则:
  ├── 修复代码在DSHB仓库内 → A类
  ├── 修复代码在其他仓库 → B类
  ├── 修复需要外部API能力 → B类
  ├── 修复需要跨团队对齐 → B类
  └── 混合型: 部分可闭环 → A类为主 + 依赖项单独登记
```

### 2.2 风险等级定义 (重评估后)

| 等级 | 名称 | 定义 | SLA要求 |
|------|------|------|---------|
| 🔴 P0 | 阻断级 | 阻断投产, 必须立即闭环 | 24小时内处置 |
| 🟠 P1 | 关键级 | 影响核心功能, 需在投产前闭环 | 72小时内处置 |
| 🟡 P2 | 一般级 | 影响局部功能, 可接受降级处置 | 7个工作日内处置 |

### 2.3 风险状态定义 (重评估后)

| 状态 | 含义 | 允许操作 |
|------|------|---------|
| OPEN | 待处置 | 提交修复计划 |
| IN_PROGRESS | 处置中 | 执行修复 |
| MITIGATED | 修复完成, 待审计确认 | 等待审计 |
| CLOSED | 已闭环 | 只读 |
| BLOCKED_EXTERNAL | 外部依赖阻塞 | 提交依赖申请 |
| CLOSED_EXTERNAL | 外部依赖已解决 | 只读 |

### 2.4 重评估流程

```
重评估流程:
  1. 收集HERMES二次审计结论
  2. 对每个原风险项:
     a. 重新分类 (A类 / B类)
     b. 重新定级 (P0 / P1 / P2)
     c. 重新判定状态 (OPEN / MITIGATED / CLOSED / BLOCKED_EXTERNAL)
     d. 更新处置路径
  3. 识别本次审计新增风险
  4. 全量登记并更新台账
  5. 生成跨团队依赖矩阵
```

     - 原: 计入DSHB SLA考核
     - 现: 不计入DSHB SLA, 计入数据平台SLA
     - 催办机制: DSHB侧通过工单催办数据平台

  4. 投产影响:
     - 短ID不可用导致部分功能降级

## §1 概述

### 1.1 背景

DSHB V86 RC2 项目 Phase 5 阶段进入跨团队指标对齐与基线一致性核验期。HERMES 自动基线扫描器于 2026-10-17 完成对当前 WAL (Write-Ahead Log) 存储层的全量性能基线采集，发现三项关键风险：

| 编号 | 定级 | 问题描述 |
|------|------|----------|
| **P1** | 🔴 严重 | 事件检索线性扫描退化，随着事件量增长查询延迟线性/超线性增长 |
| **P2-B02** | 🟡 中等 | 新增复合索引导致空间膨胀，需评估长期增长趋势 |
| **P2-B03** | 🟡 中等 | WAL 文件尺寸增大导致写入吞吐非线性下降，需定义压缩/分片策略 |

当前 WAL 存储层仅基于 `event_id` (主键) 建立 B-tree 索引，所有非主键查询 (按事件类型、时间范围、源团队) 均退化为**全量线性扫描**。HERMES 建议在复合索引 `(event_type, timestamp_range, source_team)` 之上实现 O(log n) 检索。

本评估报告对 HERMES 提出的三项问题进行逐层深度分析，输出复合索引方案的可行性评估、性能预估、资源开销计算及风险缓解策略。

### 1.2 评估范围

| 评估维度 | 覆盖内容 |
|----------|----------|
| **检索性能** | 5K → 1.17M 事件量区间的查询延迟退化曲线；复合索引前后对比 |

| **灰度影响** | 对 G1 灰度放量节奏、P99 延迟门槛的影响评估 |
| **生产影响** | 索引创建对在线服务的影响窗口、回滚方案、兼容性 |

### 1.3 评估目标

1. **量化定级**: 验证 HERMES P1 定级是否准确，确认是否存在 P0 升级场景
2. **方案评估**: 对复合索引方案进行全维度评估 (性能、空间、写入、运维)
3. **实施排期**: 明确 G1 上线前的必须完成动作与时间窗口
4. **风险闭环**: 输出风险登记条目，确保上线后长期监控覆盖

## §2 问题定级与影响分析

### 2.1 P1: 检索线性扫描退化

#### 2.1.1 退化曲线分析

HERMES 基于生产基线采集的检索延迟数据如下 (查询模式: `event_type='AUDIT' AND timestamp_range IN [T-24h, T] AND source_team='CORE'`)：

| 事件量 (N) | 线性扫描延迟 | P99 延迟 | 相对退化倍数 (vs 5K) | 延迟等级 |
|------------|-------------|----------|---------------------|----------|
| **5,000** | 12 ms | 15 ms | 1.0× | 🟢 正常 |
| **20,000** | 48 ms | 58 ms | 4.0× | 🟢 正常 |
| **100,000** | 240 ms | 295 ms | 20.0× | 🟡 警告 |
| **500,000** | 1,200 ms | 1,520 ms | 100.0× | 🟠 严重 |
| **1,170,000** | 2,808 ms | 3,625 ms | 234.0× | 🔴 致命 |

**退化模型拟合:**

线性扫描的理论复杂度为 O(n)。实测数据拟合为：

```
search_latency_ms ≈ 0.0024 × N + 8.5   (线性拟合, R² = 0.997)
```

其中截距 8.5 ms 为 WAL B-tree 主键查找的固有开销 (即使命中索引，仍需解析返回列)。

**P99 与 P50 发散分析:**

P99 延迟在 N=500K 时达到 1,520 ms，与 P50 (1,200 ms) 的比值为 1.27×；在 N=1.17M 时 P99 (3,625 ms) / P50 (2,808 ms) = 1.29×。P99/P50 比值稳定在 1.27–1.29 区间，表明线性扫描的尾部延迟并非由并发争用导致，而是**单次查询本身在数据密集区间的随机内存访问开销**。

**关键阈值分析:**

```
查询延迟门槛定义 (DSHB V86 规范):
  - 正常: ≤ 50 ms
  - 警告: 50 ms < 延迟 ≤ 200 ms
  - 严重: 200 ms < 延迟 ≤ 1000 ms
  - 致命: > 1000 ms (触发 P99 告警, 需人工介入)
```

| 阈值突破点 | 事件量 | 状态 |
|------------|--------|------|
| 警告阈值 (50 ms) | ~21K events | 🟢 当前低于此值 |
| 严重阈值 (200 ms) | ~81K events | 🟡 灰度放量将快速穿越 |
| 致命阈值 (1000 ms) | ~415K events | 🔴 灰度全量后必然触发 |

#### 2.1.2 影响范围分析

当前 WAL 层支持四类查询模式，受线性扫描退化的影响程度不同：

| 查询模式 | 示例 | 当前是否索引 | 退化程度 | 灰度阶段影响 |
|----------|------|-------------|----------|-------------|
| **按 event_id 精确查询** | `WHERE event_id = 'evt_abc123'` | ✅ B-tree 主键 | O(log n)，不退化 | ✅ 无影响 |
| **按事件类型查询** | `WHERE event_type = 'AUDIT'` | ❌ 全表扫描 | O(n)，严重退化 | 🔴 G1 起即受影响 |
| **按时间范围查询** | `WHERE timestamp BETWEEN T-24h AND T` | ❌ 全表扫描 | O(n)，严重退化 | 🔴 G1 起即受影响 |
| **组合查询 (三字段)** | `WHERE event_type=? AND timestamp=? AND source_team=?` | ❌ 全表扫描 | O(n)，严重退化 | 🔴 G1 全量后致命 |

**具体影响场景:**

1. **审计日志查询** — 每次审计查询均需扫描全量 WAL，1.17M 事件时单次查询耗时 2.8s，远超 DSHB 告警阈值
2. **事件回放 (Event Replay)** — 灰度回滚时的事件回溯查询将阻塞数秒，延长 MTTR
3. **跨团队指标对齐** — Phase5 本身需要对齐多团队事件时间戳，频繁范围查询导致对齐周期从分钟级膨胀至小时级
4. **告警规则评估** — 告警引擎按时间窗口聚合事件，在 100K+ 事件时延迟突破 200 ms 警告线

#### 2.1.3 对灰度放量的影响

DSHB V86 RC2 G1 灰度放量计划如下：

| 灰度阶段 | 时间窗口 | 预估事件量 | 预估查询延迟 | P99 状态 | 风险 |
|----------|---------|-----------|-------------|----------|------|
| G1-0 (金丝雀) | Day 1 | ~10K | ~32 ms | 🟢 正常 | 无 |
| G1-25% | Day 2 | ~30K | ~80 ms | 🟡 警告 | 需关注 |
| G1-50% | Day 3 | ~60K | ~153 ms | 🟡 警告 | 需缓解 |
| G1-75% | Day 4 | ~90K | ~225 ms | 🟠 严重 | 需缓解 |
| G1-100% (全量) | Day 5 | ~1,170K | 2,808 ms | 🔴 致命 | **上线阻断** |

**关键发现:**

- 灰度推进至 **G1-50%** (Day 3) 时，组合查询延迟突破警告阈值 (200 ms)，触发 HERMES 告警
- 灰度推进至 **G1-75%** (Day 4) 时，延迟进入严重区间 (>200 ms)，可能影响灰度面板可视化
- **G1-100% 全量放量前，复合索引必须上线**，否则 P99 延迟将突破 3.5 秒，触发生产级 P0 告警

> ⚠️ **灰度阻断点:** 建议在灰度至 G1-50% 时，必须完成复合索引创建并验证通过，否则暂停灰度推进。

### 2.2 P2-B02: 索引膨胀

#### 2.2.1 空间开销分析

**当前状态 (单一 B-tree 主键索引):**

| 项目 | 数值 |
|------|------|
| WAL 文件总大小 (1.17M events) | ~11.7 MB |
| 当前索引大小 (event_id B-tree) | ~585 KB |
| 索引/WAL 比值 | 4.98% |
| 单条事件索引开销 | ~0.51 KB / 1K events |

**复合索引方案 (新增 3 个索引):**

假设新增三个索引：
1. `idx_event_type` — 按 `event_type` 分类索引
2. `idx_timestamp` — 按 `timestamp` 范围索引
3. `idx_source_team` — 按 `source_team` 分类索引

> **注:** HERMES 方案建议 `(event_type, timestamp_range, source_team)` 三列复合索引。考虑到索引利用率和创建成本，本评估提供两种方案对比。

| 索引方案 | 索引数量 | 每 1K events 增量 | 1.17M events 总增量 | 索引总计 | 占比 |
|----------|---------|-------------------|---------------------|---------|------|
| 方案 A: 单列索引 × 3 | 4 (含主键) | ~0.51 KB | ~1.755 MB | ~2.34 MB | 18.6% |
| 方案 B: 三列复合索引 × 1 | 2 (主键 + 复合) | ~0.62 KB | ~0.725 MB | ~1.31 MB | 10.8% |

**方案推荐:**

- **方案 A (三单列索引)** — 索引利用率高，单个查询只需扫描 1/3 数据量，但创建/维护开销较大
- **方案 B (三列复合索引)** — 空间效率更高，三字段组合查询场景一次索引覆盖，但不支持单独按 timestamp 或 source_team 检索

考虑到 DSHB V86 审计查询的主要模式为三字段组合查询，**推荐方案 B (复合索引)**，同时在后续迭代中评估是否需要补充 `idx_timestamp` 单列索引以支持纯时间范围查询。

#### 2.2.2 增长趋势预测

基于当前生产环境的日均事件写入量 (~35,000 events/day, 峰值 52,000 events/day)，预测 7/30/90 天索引空间增长：

| 时间窗口 | 累计事件量 | WAL 文件大小 | 索引总量 (方案 B) | 索引/WAL 占比 | 磁盘空间预估 |
|----------|-----------|-------------|-------------------|--------------|-------------|
| 当前 | 1.17M | 11.7 MB | 1.31 MB | 10.8% | 13.0 MB |
| **+7 天** | 1.415M | 14.15 MB | 1.57 MB | 11.1% | 15.7 MB |
| **+30 天** | 2.22M | 22.2 MB | 2.45 MB | 11.0% | 24.7 MB |
| **+90 天** | 4.315M | 43.15 MB | 4.78 MB | 11.1% | 47.9 MB |

**增长曲线特征:**

```
事件增长模型: N(t) = N₀ + r × t    (r = 日均写入速率, ~35K/day)
索引空间:    S(t) = N₀ × s₀ + r × t × s₀   (s₀ = 单事件索引空间)
WAL 空间:    W(t) = N₀ × w₀ + r × t × w₀   (w₀ = 单事件 WAL 空间)
```

索引/WAL 比值保持恒定 (~10.8–11.1%)，因为索引和 WAL 的容量单位线性相关。**索引膨胀本身不构成独立风险**，但需注意以下场景：

1. **长期累积 (90+ 天):** 索引总量接近 5 MB，若未启用 WAL 压缩/清理策略，磁盘空间将成为瓶颈
2. **索引重建窗口:** 每次索引重建需要额外临时空间 (约等于索引本身大小)，峰值磁盘占用翻倍
3. **多实例部署:** 若 DSHB 部署多实例 (replica)，每个副本独立维护索引，总磁盘消耗 = 单实例 × 副本数

> ✅ **结论:** 方案 B 在 90 天内索引总量可控 (<5 MB)，不构成独立风险。但需纳入 P2-B03 (WAL 非线性增长) 联动评估。

### 2.3 P2-B03: WAL 非线性增长

#### 2.3.1 写入延迟退化曲线

HERMES 基线采集的 WAL 写入延迟数据 (单次 batch 写入 100 events):

| WAL 文件大小 | 写入延迟 (P50) | 相对退化 | 写入吞吐 (events/s) | 状态 |
|-------------|----------------|---------|---------------------|------|
| 1 MB | 2.1 ms | 基准 | 47,619 | 🟢 正常 |
| 5 MB | 2.3 ms | +9.5% | 43,478 | 🟢 正常 |
| 10 MB | 2.5 ms | +19.0% | 40,000 | 🟢 正常 |
| **50 MB** | **3.8 ms** | **+81.0%** | 26,316 | 🟡 警告 |
| **100 MB** | **5.6 ms** | **+166.7%** | 17,857 | 🔴 严重 |

**退化曲线拟合:**

```
write_latency_ms ≈ 2.1 × (1 + 0.0088 × WAL_size_MB)
```

退化速率在 50 MB 后加速，符合 WAL 文件追加写入时磁盘 I/O 调度退化的典型模式 — 当 WAL 文件跨越磁盘分区边界或操作系统 page cache 驱逐阈值时，延迟跳变显著。

**当前 WAL 自动轮转策略:**

```
轮转触发条件:
  - WAL 文件达到 50 MB 阈值 → 关闭当前文件, 创建新文件
  - 轮转频率 (日均): ~35K events/day / (50MB / 11.7MB per 1.17M events)
    ≈ 35K / 4.7K per 50MB ≈ 7.4 次/天
  - 日均 WAL 生成量: ~35K events × 10 bytes/event ≈ 350 KB/day (当前)
    → 预计 143 天后单文件达到 50 MB 触发轮转

注: 若写入速率增加至 300K events/day (灰度全量+多团队接入),
    日均 WAL 生成量 ≈ 3 MB/day → 17 天后触发轮转
```

#### 2.3.2 对审计吞吐的影响

**正常写入场景 (WAL < 50 MB):**

| 指标 | 数值 |
|------|------|
| 写入吞吐 | 47,619 events/s |
| 批量写入延迟 (100 events) | 2.1 ms |
| 审计日志延迟 (端到端) | 5 ms |
| 告警评估窗口 | 500 ms |

**临界写入场景 (WAL 接近 50 MB):**

| 指标 | 数值 | 变化 |
|------|------|------|
| 写入吞吐 | 26,316 events/s | ↓ 44.7% |
| 批量写入延迟 | 3.8 ms | ↑ 81% |
| 审计日志延迟 | 9.2 ms | ↑ 84% |
| 告警评估窗口 | 850 ms | ↑ 70% |

**退化影响分析:**

1. **审计日志延迟 (9.2 ms)** — 仍远低于 50 ms 警告线，写入吞吐退化对审计可观测性影响可控
2. **告警评估窗口 (850 ms)** — 在 500 ms 预期窗口基础上退化 70%，可能导致告警延迟 350 ms，触发**告警风暴 (alert storm)**
3. **灰度流量冲击** — 灰度放量期间事件写入速率可能瞬时提升 3–5 倍 (从 35K 到 105K–175K events/s)，若恰好叠加 WAL 接近 50 MB 临界值，写入延迟可能突破 10 ms

**推荐 WAL 压缩/分片策略:**

| 策略 | 描述 | 收益 | 实施复杂度 |
|------|------|------|-----------|
| **策略 A: 提前轮转阈值** | 将 50 MB 阈值下调至 20 MB | 降低峰值延迟至 ~4.5% | 🟢 低 (配置变更) |
| **策略 B: WAL 压缩** | 对已轮转的历史 WAL 进行 LZ4/Zstd 压缩 | 磁盘空间节省 ~70% | 🟡 中 (代码改动) |
| **策略 C: WAL 分片** | 按 `source_team` 分片，每片独立 WAL | 消除单文件大小瓶颈 | 🔴 高 (架构变更) |

> **建议:** 短期采用策略 A (阈值下调至 20 MB)，中期在 V87 中引入策略 B (WAL 压缩)。策略 C 需跨版本规划。

## §3 复合索引方案评估

### 3.1 索引设计

#### 3.1.1 索引 Schema 定义

**推荐方案: 三列复合索引 (方案 B)**

```sql
-- 索引名称: idx_search_composite
-- 创建语句 (伪 SQL):
CREATE INDEX idx_search_composite
ON wal_events (
    event_type    ASC,   -- 分类索引, 低基数, 高选择性
    timestamp     DESC,  -- 范围索引, 最新事件优先 (审计场景)
    source_team   ASC    -- 分类索引, 低基数
);
```

**索引列顺序设计原则:**

| 列位置 | 列名 | 选择率 | 索引作用 | 查询模式 |
|--------|------|--------|----------|---------|
| 第 1 列 | `event_type` | ~5 个值 (高选择性) | 分区定位，快速缩小扫描范围 | `WHERE event_type = ?` |
| 第 2 列 | `timestamp` | 连续 (极高选择性) | 范围扫描，支持 T-24h 回溯 | `AND timestamp BETWEEN ? AND ?` |
| 第 3 列 | `source_team` | ~12 个值 (中低选择性) | 最终过滤，避免回表 | `AND source_team = ?` |

**列顺序选择理由:**

1. **event_type 首列:** 审计查询几乎总包含事件类型条件，首列过滤可将扫描范围从 N 缩减至 N/5
2. **timestamp 第二列:** B-tree 支持范围查询，降序排列使最近事件优先匹配，减少范围扫描的物理页读取
3. **source_team 第三列:** 作为复合索引的最终列，避免回表查找，使查询完全通过索引完成 (index-only scan)

#### 3.1.2 索引大小估算

| 100,000 | ~71.5 KB | ~51.3 KB | ~122.8 KB | ~1 MB | 12.3% |
| 500,000 | ~357.5 KB | ~256.5 KB | ~614.0 KB | ~5 MB | 12.3% |
| 1,170,000 | ~855.3 KB | ~596.3 KB | ~1.44 MB | ~11.7 MB | 12.3% |

### 3.2 性能提升预估

#### 3.2.1 检索延迟对比 (Before / After)

基于复合索引理论收益 (O(log n) 扫描替代 O(n) 线性扫描) 和实测基准推算:

| 查询模式 | 事件量 | 优化前延迟 | 优化后延迟 (预估) | 提升倍数 | 状态变化 |
|----------|--------|-----------|-------------------|---------|---------|
| `event_type + timestamp + source_team` | 5K | 12 ms | **1.2 ms** | **10×** | 🟢→🟢 |
| `event_type + timestamp + source_team` | 20K | 48 ms | **1.5 ms** | **32×** | 🟢→🟢 |
| `event_type + timestamp + source_team` | 100K | 240 ms | **2.1 ms** | **114×** | 🟡→🟢 |
| `event_type + timestamp + source_team` | 500K | 1,200 ms | **3.2 ms** | **375×** | 🔴→🟢 |
| `event_type + timestamp + source_team` | 1.17M | 2,808 ms | **4.8 ms** | **585×** | 🔴→🟢 |
| `event_type` (仅首列) | 1.17M | 2,808 ms | **1.8 ms** | **1,560×** | 🔴→🟢 |
| `event_type + timestamp` (前两列) | 1.17M | 2,808 ms | **3.5 ms** | **802×** | 🔴→🟢 |

> **注:** 优化后延迟预估基于 B-tree 索引查找的理论下界 (3–5 次索引页读取 + 1 次数据行读取)。实际延迟取决于 WAL B-tree 的填充因子 (page fill factor) 和存储介质 I/O 性能。上述数值假设 page fill factor = 90%，存储为 SSD (随机读 0.1 ms/op)。

#### 3.2.2 查询模式覆盖分析

| 查询模式 | 复合索引覆盖率 | 索引可用性 | 备注 |
|----------|--------------|-----------|------|
| `event_type = ?` | 100% | ✅ 使用首列 | 完全利用索引 |
| `event_type = ? AND timestamp = ?` | 100% | ✅ 使用前两列 | 范围扫描高效 |
| `event_type = ? AND source_team = ?` | ~50% | ⚠️ 仅用首列，第三列需回表 | 第三列不连续，无法完全索引覆盖 |
| `timestamp = ?` (无 event_type) | 0% | ❌ 不使用索引 | 纯时间范围查询需单独索引 |
| `source_team = ?` (无 event_type) | 0% | ❌ 不使用索引 | 需单独索引 |
| `event_id = ?` | 100% | ✅ 主键索引 | 不受影响 |

**缺口分析:**

- 纯时间范围查询 (`WHERE timestamp BETWEEN ? AND ?`) 和纯 source_team 查询无法利用复合索引
- 当前 DSHB V86 审计场景以三字段组合查询为主 (占查询总量 ~85%)，缺口影响可控
- 建议在 V87 规划中补充 `idx_timestamp` 单列索引以覆盖纯时间范围查询场景

### 3.3 资源开销

#### 3.3.1 空间开销

| 项目 | 当前 (无复合索引) | 新增复合索引后 | 增量 |
|------|------------------|---------------|------|
| 主键索引大小 (1.17M events) | 596.3 KB | 596.3 KB | — |
| 复合索引大小 | — | 855.3 KB | +855.3 KB |
| 索引总量 | 596.3 KB | 1.44 MB | +142% |
| WAL 数据大小 | 11.7 MB | 11.7 MB | — |
| 磁盘总占用 | 12.29 MB | 13.14 MB | +7.0% |
| 索引/WAL 比 | 4.98% | 12.34% | +148% |
| 峰值磁盘占用 (索引重建时) | 12.89 MB | 14.00 MB | +10.9% |

> **重建时临时空间说明:** B-tree 索引重建时需在内存中构建临时副本后原子替换，峰值磁盘占用 = 当前索引 + 重建索引副本 ≈ 索引大小 × 2。1.17M 事件时峰值 ~14.0 MB，仍在可接受范围。

#### 3.3.2 写入开销

索引维护的写入开销取决于索引更新频率和 B-tree 层级深度:

| 操作 | 当前 (仅主键索引) | 新增复合索引后 | 增幅 |
|------|------------------|---------------|------|
| 单事件写入 | 1 次索引更新 | 2 次索引更新 | +100% |
| 单事件写入延迟 | 0.8 μs | 1.6 μs | +0.8 μs |
| 批量写入 (100 events) | 82 μs | 165 μs | +101% |
| 批量写入后额外延迟 | — | +83 μs | — |
| 写入吞吐 (events/s) | 47,619 | ~47,000 | -1.3% |

**写入影响评估:**

- 单事件写入延迟增加 0.8 μs，对批量写入 (100 events batch) 的影响约为 83 μs
- 在 35K events/s 日均写入速率下，额外延迟总量 = 35,000 × 0.8 μs = 28 ms/second
- **结论:** 写入开销增幅 ~1.3%，对批量写入吞吐的影响可忽略不计

#### 3.3.3 内存开销

索引页需常驻内存 (或 page cache) 以支持快速查找。复合索引的内存占用取决于 B-tree 层级结构:

| 事件量 | 复合索引页数 (4KB/page) | 内存占用 (全缓存) |
|--------|------------------------|-------------------|
| 5,000 | 1 页 (根页) | 4 KB |
| 20,000 | 2 页 | 8 KB |
| 100,000 | 3 页 | 12 KB |
| 500,000 | 3 页 | 12 KB |
| 1,170,000 | 4 页 | 16 KB |

> 复合索引在 1.17M 事件量下仅需 4 层 B-tree (4 KB/page, fill factor 90%)，内存占用仅 16 KB，不构成额外负担。

### 3.4 创建时机

#### 3.4.1 三种时机对比

| 创建时机 | 优势 | 劣势 | 推荐度 |
|----------|------|------|--------|
| **灰度前 (预创建)** | 灰度全程无需索引重建；灰度推进无延迟突变 | 预创建需处理当前 1.17M 存量数据；需暂停或降级查询 | ⭐⭐⭐⭐⭐ 强烈推荐 |
| **灰度中 (在线创建)** | 无需暂停服务；可分阶段观察效果 | 创建期间查询性能不稳定；索引与 WAL 不一致窗口 | ⭐⭐ 不推荐 |
| **灰度后 (回填)** | 不影响灰度过程；数据量确定后一次性构建 | 全量回填耗时；灰度期间仍受线性扫描退化影响 | ⭐ 仅限紧急情况 |

**推荐: 灰度前预创建**

理由:
1. 当前存量 1.17M 事件，预创建耗时约 45–60 秒 (基于批量索引构建速度 ~25K events/s)
2. 灰度全程无需担心索引退化，查询性能从 Day 1 即达标
3. 创建窗口可安排在灰度准备期 (当前至 Day 1 之间的维护窗口)

#### 3.4.2 索引创建流程

```
时间线 (灰度前维护窗口, 建议 02:00–04:00 UTC):

T+0min    开始索引构建 (BUILD INDEX idx_search_composite)
T+0min    记录索引创建开始时间戳
T+0min    暂停审计日志写入 (写入进入 WAL 暂存队列)
T+45min   索引构建完成
T+46min   执行索引验证 (CHECK INDEX INTEGRITY)
T+48min   恢复审计日志写入 (flush 暂存队列至 WAL)
T+50min   执行查询性能回归测试 (验证延迟 ≤ 50 ms)
T+52min   确认通过，开启灰度
```

**索引验证脚本 (伪代码):**

```python
# 验证脚本: validate_index_consistency.py
def validate_index_consistency():
    # 1. 索引完整性检查
    row_count = count_all_events()         # 全表扫描计数
    indexed_count = count_indexed_events()  # 索引计数
    assert row_count == indexed_count, f"Index inconsistency: {row_count} != {indexed_count}"
    
    # 2. 查询正确性验证
    for test_query in generate_test_queries():
        result_indexed = execute_with_index(test_query)
        result_fullscan = execute_with_fullscan(test_query)
        assert result_indexed == result_fullscan, f"Query mismatch: {test_query}"
    
    # 3. 性能回归验证
    latency_p50 = measure_latency_p50()
    latency_p99 = measure_latency_p99()
    assert latency_p50 <= 50, f"P50 latency breach: {latency_p50}ms"
    assert latency_p99 <= 100, f"P99 latency breach: {latency_p99}ms"
    
    # 4. 写入回归验证
    write_throughput = measure_write_throughput()
    assert write_throughput >= 40000, f"Write throughput degraded: {write_throughput} events/s"
    
    return {"status": "PASSED", "latency_p50": latency_p50, "latency_p99": latency_p99,
            "write_throughput": write_throughput}
```

### 3.5 生产环境影响评估

#### 3.5.1 影响矩阵

| 影响维度 | 影响程度 | 影响时长 | 缓解措施 |
|----------|---------|---------|----------|
| **写入暂停** | 🟡 短暂 (45–60 min) | 维护窗口内 | 预安排在低流量时段 (02:00 UTC) |
| **查询延迟波动** | 🟢 创建期间查询性能退化 | 索引构建过程中 | 查询流量路由至只读副本 |
| **磁盘 I/O** | 🟡 短暂 I/O 密集 | 索引构建期间 (~45 min) | 使用 `cpulimit` 限制构建 CPU 占用 |
| **存储容量** | 🟢 增量 ~14.0 MB | 持久 | 在 50 GB SSD 上可忽略 |
| **灰度延迟** | 🟢 无延迟突变 | 全程 | 预创建方案保证灰度全程稳定 |
| **回滚风险** | 🟢 低风险 | 可逆操作 | DROP INDEX 命令即可回滚 |

#### 3.5.2 回滚方案

```sql
-- 回滚步骤:
-- 1. 删除复合索引 (保留主键索引)
DROP INDEX idx_search_composite ON wal_events;

-- 2. 验证回滚
SELECT * FROM wal_events WHERE event_type = ? -- 应恢复线性扫描 (性能退化但功能正确)

-- 3. 清理临时空间
VACUUM wal_events;
```

**回滚时间:** DROP INDEX 操作耗时约 30 秒 (与创建速度相当)。**回滚后风险:** 查询延迟恢复至线性扫描水平，但在灰度前维护窗口中完成回滚不会影响灰度计划。

#### 3.5.3 并发兼容性

- **读并发:** 索引创建期间，查询可路由至只读副本 (read replica)，不影响主服务
- **写并发:** 索引创建期间暂停写入 (~45–60 min)，写入流量缓存至 WAL 暂存队列，创建完成后 flush
- **灰度兼容性:** 灰度期间无新增索引操作，查询性能稳定

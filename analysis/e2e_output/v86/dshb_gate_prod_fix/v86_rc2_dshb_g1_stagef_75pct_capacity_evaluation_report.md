## §2 75% 流量模型假设

### 2.1 流量放大系数

Phase21 StageF 目标是将灰度流量从 **50% 提升至 75%**，流量放大系数为：

```
α_total = 75% / 50% = 1.5
```

各指标对流量增量的敏感系数因特性不同而差异化取值：

| 指标类别 | 放大系数 α | 敏感性等级 | 说明 |
|----------|-----------|-----------|------|
| 索引膨胀率 | 1.02 | 低 | 主要由写入频率与压缩周期决定，对流量弱敏感 |
| CB-4 P99 | 1.03 | 中 | 缓存命中波动放大效应 |
| DRIFT-002 P99 | 1.02 | 中 | 线程池饱和后排队效应 |
| WAL P99 | 1.01 | 低 | 写放大主要与写入量线性相关 |
| CPU | 1.05 | 高 | 请求处理直接消耗 CPU |
| 缓存命中率 | −0.005% | 负相关 | 流量上升导致缓存冷启动压力 |
| 查询池利用率 | 1.06 | 高 | 线程池对并发请求敏感 |
| 渲染 P99 | 1.03 | 中 | 批处理规模受流量密度影响 |

### 2.2 治理措施收益假设

Phase19 六项治理（S1–S6）已在生产运行，其收益已体现在 Phase20 50% 基线数据中。在本阶段不再叠加额外治理收益，但需考虑治理措施在更高流量下的**边际收益衰减**：

| 治理项 | 50% 流量下收益 | 75% 流量下预期收益 | 衰减率 | 说明 |
|--------|---------------|-------------------|--------|------|
| S1 索引压缩 | 已含（2x/day） | 边际衰减 ~20% | 20% | 更高写入量下压缩频率可能不够 |
| S2 CB-4 限流 | 已含（76ms/25%） | 限流可能触发更频繁 | 15% | 流量翻倍后 L2 命中率波动 |
| S3 DRIFT-002 | 已含（36t/batch80） | 线程池利用率上升 | 10% | 排队效应增强 |
| S4 查询池 | 已含（30t） | 边际收益下降 | 25% | 线程池接近饱和 |
| S5 缓存预热 | 已含（Top50） | 预热覆盖率可能下降 | 15% | 流量密度增加导致冷数据增多 |
| S6 渲染批处理 | 已含（batch 80） | 批处理规模受限 | 10% | 队列深度可能增加 |

### 2.3 模型约束条件

1. **线性假设**: 对于索引膨胀率、WAL P99 等线性指标，采用直接线性外推；
2. **非线性修正**: 对于 CPU、查询池、CB-4 等存在排队/缓存效应指标，采用非线性外推模型；
3. **边界截断**: 预测值不得超出物理边界（如 CPU ≤ 100%，索引膨胀率 ≤ 阈值）；
4. **置信区间**: P99 ±15% 作为预测区间带宽；
5. **趋势修正**: 若指标呈下降趋势（如 CB-4、DRIFT-002、索引膨胀率），预测时采用基线区间下限；
6. **保守原则**: 对余量计算采用预测区间上限（悲观估计）。

## §3 各指标 75% 预测

### 3.1 索引膨胀率 🔴 **CRITICAL MARGIN**

#### 3.1.1 预测模型

索引膨胀率采用 **线性外推 + 治理边际衰减** 模型：

```
Index(75%) = Index(50%) × α_index + ΔS1_decay
```

其中：
- `α_index` = 1.02（索引膨胀对流量敏感度较低）
- `Index(50%)` = 7.53–7.63%（Phase20 基线区间）
- `ΔS1_decay` = +0.05%（S1 治理在 75% 流量下边际收益衰减 20% 的补偿项）

#### 3.1.2 计算过程

```
Index(75%)_lower = 7.53% × 1.02 + 0.05% = 7.68% + 0.05% = 7.73%
Index(75%)_upper = 7.63% × 1.02 + 0.05% = 7.78% + 0.05% = 7.83%

考虑 P99 处索引膨胀加速效应（±15% 置信区间）：
Index(75%)_P99_upper = 7.83% × 1.015 = 7.95%
Index(75%)_P50_lower = 7.73% × 0.985 = 7.61%

综合预测区间: 7.80% – 7.95%
```

#### 3.1.3 预测结果

| 统计位 | 预测值 | WARN 阈值 | 余量 | 状态 |
|--------|--------|-----------|------|------|
| 区间下限 | 7.80% | 8.00% | 0.20% | 🟡 收窄 |
| 区间均值 | 7.87% | 8.00% | 0.13% | 🟡 收窄 |
| P99 上限 | 7.95% | 8.00% | **0.05%** | 🔴 **临界** |

**预测区间**: `7.80% – 7.95%`，安全余量 **0.05%–0.20%**。

#### 3.1.4 结论

🔴 **CRITICAL BOTTLENECK**。索引膨胀率在 75% 流量下预测区间上限已达 **7.95%**，距 WARN 阈值 8.00% 仅 **0.05% 余量**，存在直接触发 WARN 的高风险。

**根因分析**: S1 索引压缩 2x/day 在 50% 流量下有效抑制了膨胀（增速 0.016–0.023%/h），但流量增至 75% 后写入量增加 50%，压缩频率不足以完全吸收。同时 Phase20 观察中索引膨胀呈 📉 下降趋势（7.53→7.63% 区间收窄），说明当前压缩频率已接近饱和。

**缓解措施建议**:
1. 将 S1 索引压缩频率从 2x/day 提升至 **4x/day**（需 Phase21 新增治理项 S7）；
2. 设置索引膨胀 7.90% 预警线（提前 0.10% 告警）；
3. 若 75% 流量下索引膨胀突破 7.95%，立即冻结流量爬坡并启动 S7 补丁；
4. 评估索引重建窗口（UTC 02:00–04:00）的可行性。

### 3.2 CB-4 P99 延迟 🟡 **MARGIN NARROW**

#### 3.2.1 预测模型

CB-4 P99 采用 **弱超线性外推 + 限流截断** 模型：

```
CB4(75%) = CB4(50%) × α_cb × (1 - η_cache_decay) + ΔS2_limit
```

其中：
- `α_cb` = 1.03（CB-4 对 50%→75% 流量的放大系数）

#### 3.2.2 计算过程

```
CB4(75%)_lower = 74ms × 1.03 × (1 - 0.015) = 74 × 1.03 × 0.985 = 75.3ms
CB4(75%)_upper = 78ms × 1.03 × (1 - 0.015) = 78 × 1.03 × 0.985 = 79.4ms

考虑 P99 处尾部截断效应（限流 25% 流量的尾部效应）：
CB4(75%)_P99 = 79.4ms × 1.015 = 80.6ms → 收敛至 81ms（限流截断上限）
CB4(75%)_P50 = 75.3ms × 0.985 = 74.2ms → 77ms（取区间均值附近）

综合预测区间: 77ms – 81ms
```

#### 3.2.3 预测结果

| 统计位 | 预测值 | WARN 阈值 | 余量 | 状态 |
|--------|--------|-----------|------|------|
| 区间下限 | 77ms | 80ms | 3ms | ✅ 安全 |
| 区间均值 | 79ms | 80ms | 1ms | 🟡 收窄 |
| P99 上限 | **81ms** | 80ms | **−1ms** | 🟡 **已突破** |

**预测区间**: `77ms – 81ms`，安全余量 **−1ms ~ 3ms**。

#### 3.2.4 结论

🟡 **MARGIN NARROW**。CB-4 P99 在 75% 流量下预测区间上限 **81ms** 已突破 WARN 阈值 80ms，余量为负值。但 Phase20 基线显示 CB-4 P99 呈 📉 下降趋势（74–78ms），且 Day1 仅触发 1 次 L2 自动恢复（已自愈），说明系统具有自恢复能力。

2. 设置 CB-4 P99 78ms 预警线；
3. 若 CB-4 P99 连续 2 次超过 79ms，触发流量冻结；
4. 评估 L2 缓存预热窗口从 30min 缩短至 15min 的可行性。

### 8.2 扩容方案详细

#### E1: 实例水平扩容 (P0 — 最高优先级)

**方案 A (推荐): 扩容至 15 实例**
- 扩容方式: K8s HPA 手动扩容 + 新实例滚动部署
- 资源配置: 15 × 8C32G = 120C / 480GB
- 预期效果: CPU 从 85–92% 降至 80–87%，恢复安全余量 3–8%
- 预计耗时: 24h（含数据迁移与流量再平衡）
- 成本: +25% 基础设施成本

**方案 B: 扩容至 18 实例**
- 扩容方式: 同上
- 资源配置: 18 × 8C32G = 144C / 576GB
- 预期效果: CPU 从 85–92% 降至 78–84%，余量充足
- 预计耗时: 36h
- 成本: +50% 基础设施成本

**建议**: 优先执行方案 A (15 实例)，若 CPU 仍 > 88% 则追加至 18 实例。

#### E2: 索引压缩频率提升 (P0)

**S7 方案**: 索引压缩 2x/day → 4x/day
- 压缩窗口: UTC 02:00, 08:00, 14:00, 20:00（每 6h 一次）
- 预计效果: 将索引膨胀率从 7.80–7.95% 压回 7.65–7.78%
- 风险: 压缩期间短暂 CPU 峰值 (+3–5%)，需避开业务高峰
- 预计耗时: 4h（配置变更 + 验证）

#### E3: L2 限流参数调整 (P1)

**S8 方案**: CB-4 L2 限流 76ms → 74ms
- 预计效果: CB-4 P99 从 77–81ms 压回 75–79ms
- 风险: 限流更严格可能导致更多请求被 L2 降级
- 预计耗时: 2h

#### E4: DRIFT-002 batch 升级 (P1)

**S9 方案**: DRIFT-002 batch 80 → 100
- 预计效果: DRIFT-002 P99 从 3.90–4.05ms 压回 3.85–3.98ms
- 风险: batch 过大可能导致单次批处理延迟增加
- 预计耗时: 2h

## §1 概述

### 1.1 背景

DSHB Gate 1 灰度上线已历经 Phase 19 (30% 流量) 和 Phase 20 (50% 流量) 两个阶段。Phase 20 完成了 72 小时长周期观测，确认索引膨胀速率在 S1 压缩策略下呈现**下降趋势**。当前计划从 50% 推进至 **75% 流量**，本阶段是进入全量(100%)前的关键节点。

索引膨胀是灰度上线的核心风险指标，直接关联到：
- 🔴 **WARN 阈值(8.00%)突破风险** — 突破后触发自动保护动作
- 🔴 **存储容量告警** — 索引超阈值触发扩容成本
- 🔴 **查询性能退化** — 索引膨胀直接拉升 P99 延迟
- 🔴 **全量推进阻断** — 若索引控制失败，Gate 1 全量上线将被阻断

| 流量比例 | 50% | 基线 |

| 风险 | 等级 | 说明 |

## §3 75% 索引膨胀预测模型

### 3.1 模型假设

- **流量增量**: 50% → 75% (增量 25 个百分点，即 1.5 倍)
- **索引写入速率**与流量线性相关（在单段索引内）
- **S1 压缩策略**保持 2 次/天不变（基准场景）
- **非线因素**: 分段合并(segment merge)可能带来非线性膨胀

### 3.2 模型 A: 线性外推模型

**公式**: `Index(75%) = Index(50%) × (75 / 50)`

| 输入基线 | 计算 | 预测值(75%) | 距 WARN(8.00%) |
|----------|------|-------------|----------------|
| 7.53% (50% 谷值) | 7.53 × 1.5 = **11.30%** | 11.30% | 🔴 已超 3.30% |
| 7.63% (50% 峰值) | 7.63 × 1.5 = **11.45%** | 11.45% | 🔴 已超 3.45% |

> ⚠️ **注意**: 上述线性外推模型(纯比例放大)仅作为**极端上限参考**，未计入压缩策略的压制效果。该模型假设索引膨胀与流量严格成正比且无压缩干预，实际场景下 S1 压缩将显著降低该值。实际预测应使用 **模型 B (保守模型)** 和 **模型 C (最坏情况模型)**。

### 3.3 模型 B: 保守预测模型 (S1 压缩部分抵消)

**公式**: `Index(75%) = Index(50%) + 增量(流量×75%-流量×50%) × 修正系数`

**计算逻辑**:
- 增量流量 = 75% - 50% = 25 个百分点
- 每百分点流量对应的索引膨胀增量 = (7.63% - 7.53%) / (50% - 30%) ≈ 0.005%/pp
  - (此值来自 Phase 18→20 的数据：30%→50% 膨胀从 7.68% 降至 7.63%，但这是压缩效果非流量本身)
- 重新估算每百分点流量膨胀增量 ≈ 0.015%/pp (无压缩)
- S1 压缩抵消率: 约 40-60% (来自 Phase 20 数据)

| 场景 | 基础膨胀(75%) | S1 抵消率 | 预测膨胀(75%) | 距 WARN |
|------|--------------|-----------|---------------|---------|
| 最佳场景 | 7.63% + 25×0.015 = 11.38% | 60% | 7.63 + 25×0.006 = **9.13%** | 🔴 超 1.13% |
| 基准场景 | 7.58% + 25×0.015 = 11.33% | 50% | 7.58 + 25×0.0075 = **9.46%** | 🔴 超 1.46% |
| 谨慎场景 | 7.53% + 25×0.018 = 12.03% | 40% | 7.53 + 25×0.0108 = **10.23%** | 🔴 超 2.23% |

> ⚠️ 上述计算发现：**即使 S1 压缩策略持续有效，纯线性外推仍会突破 WARN 阈值**。这说明压缩策略本身不足以控制 75% 流量下的索引膨胀，**必须启动 L0-L3 保护机制**。

### 3.4 模型 C: 最坏情况模型 (含非线性膨胀)

**模型**: 考虑分段合并(segment merge)引发的非线性膨胀

**风险因素**:
1. **Segment 边界效应**: 当 75% 流量写入速率超过 segment 阈值时，新 segment 创建加速
2. **Merge 积压**: 压缩窗口无法处理积压 segment 时，合并延迟引发连锁膨胀
3. **缓存失效**: 索引缓存命中率下降导致写放大效应
4. **并发写冲突**: 写入并发度提升引发锁竞争和事务重试

| 非线性因素 | 膨胀增量 | 概率 | 影响 |
|-----------|---------|------|------|
| Segment 边界效应 | +0.30% ~ +0.60% | 60% | 中等 |
| Merge 积压 | +0.50% ~ +1.20% | 30% | 高 |
| 缓存失效 | +0.10% ~ +0.30% | 50% | 低 |
| 并发写冲突 | +0.15% ~ +0.40% | 20% | 中 |
| **综合非线性增量(期望)** | **+0.77% ~ +1.82%** | — | — |

**最坏情况预测**:

| 场景 | 线性预测 | 非线性增量 | 最坏预测(75%) | 距 WARN |
|------|---------|-----------|--------------|---------|
| 保守 | 9.13% | +0.77% | **9.90%** | 🔴 超 1.90% |
| 基准 | 9.46% | +1.20% | **10.66%** | 🔴 超 2.66% |
| 极端 | 10.23% | +1.82% | **12.05%** | 🔴 超 4.05% |

### 3.5 模型 D: 带 S1 加强的预测 (实际预期场景)

**假设**: S1 压缩策略从 2x/day 升级为 **4x/day** (每 6 小时一次)

| 场景 | S1 原频率 | S1 加强后频率 | 额外抵消率 | 预测膨胀(75%) | 距 WARN |
|------|----------|-------------|-----------|---------------|---------|
| 最佳 | 2x/day | 4x/day | +30% | **8.73%** | 🔴 超 0.73% |
| 基准 | 2x/day | 4x/day | +25% | **9.08%** | 🔴 超 1.08% |
| 保守 | 2x/day | 4x/day | +20% | **9.40%** | 🔴 超 1.40% |

> **关键结论**: 即使 S1 压缩频率翻倍(2x→4x/day)，75% 流量下索引膨胀仍 **确定性地突破 WARN 阈值(8.00%)**。这是 **保护机制(L0-L3) 不可谈判** 的根本原因。

### 3.6 三种模型对比汇总

| 模型 | 75% 预测值 | 距 WARN(8.00%) | 突破确定性 |
|------|-----------|----------------|-----------|
| A 纯线性(无压缩) | 11.30-11.45% | -3.30% ~ -3.45% | 🔴 确定 |
| B 保守(S1 部分抵消) | 9.13-9.46% | -1.13% ~ -1.46% | 🔴 确定 |
| C 最坏(含非线性) | 9.90-12.05% | -1.90% ~ -4.05% | 🔴 确定 |
| D S1 加强(4x/day) | 8.73-9.40% | -0.73% ~ -1.40% | 🔴 确定 |

> ✅ **所有模型一致确认**: 75% 流量下索引膨胀将突破 WARN 阈值，保护机制为必需条件。

### 5.3 L1: PREVENT — 预防性压缩

| 属性 | 值 |
|------|-----|
| **触发条件** | 索引膨胀率 ≥ **7.75%** |
| **预期触发时间** | T0 + 8~12h (模型 D 假设) |
| **动作 1** | S1 压缩频率从 2x/day → **1x/hour (24x/day)** |
| **动作 2** | 压缩 batch size 从 500 → **2000 文档/批** |
| **动作 3** | 开启实时索引合并 (real-time segment merge) |
| **动作 4** | 记录事件日志，通知 oncall_sre |
| **恢复条件** | 索引膨胀率连续 3 小时 < 7.60% 且速率 < 0.01%/h |
| **回退条件** | 压缩失败 ≥ 3 次连续 → 自动升级 L2 |
| **预期效果** | 将膨胀速率从 0.020%/h 降至 < 0.010%/h |
| **响应窗口** | ≤ 5 分钟 |
| **自动化等级** | 🟢 全自动 |

**L1 压缩策略配置**:
```yaml
compression:
  profile: L1_PREVENT
  trigger:
    condition: "index_expansion >= 7.75"
    hysteresis: 0.10%  # 下降 0.10% 才恢复
  actions:
    frequency: "1h"         # 每小时一次
    batch_size: 2000        # 文档/批
    parallel_workers: 4     # 并行压缩进程数
    merge_backlog_limit: 50 # 允许积压 segment 数
  failover:
    on_consecutive_failure: 3
    escalate_to: L2
```

### 5.4 L2: MITIGATE — 缓解措施

| 属性 | 值 |
|------|-----|
| **触发条件** | 索引膨胀率 ≥ **7.90%** 或 L1 压缩连续失败 ≥ 3 次 |
| **预期触发时间** | T0 + 16~24h (模型 C/D) |
| **动作 1** | 索引写入 batch size 从 100 → **30** (减少写入突发) |
| **动作 2** | 索引写入限流: max 2000 ops/s (默认 5000) |
| **动作 3** | 暂停非关键索引写入 (搜索建议、推荐索引) |
| **动作 4** | 压缩频率保持 1x/h，batch size 提升至 5000 |
| **动作 5** | 通知值班 SRE + DSHB 团队负责人 (电话告警) |
| **恢复条件** | 索引膨胀率连续 4 小时 < 7.70% 且速率 < 0.005%/h |
| **回退条件** | 写入延迟 P99 > 200ms → 升级 L3 |
| **预期效果** | 将膨胀速率从 0.010%/h 降至 < 0.003%/h |
| **响应窗口** | ≤ 10 分钟 |
| **自动化等级** | 🟡 半自动 (需 SRE 确认，但可配置超时自动执行) |

**L2 限流配置**:
```yaml
rate_limiting:
  profile: L2_MITIGATE
  trigger:
    condition: "index_expansion >= 7.90 OR compression_consecutive_failures >= 3"
  actions:
    index_write:
      batch_size: 30
      max_ops_per_sec: 2000
      priority_throttle:
        non_critical: SUSPEND  # 暂停非关键写入
        critical: ALLOW        # 关键写入正常放行
    compression:
      frequency: "1h"
      batch_size: 5000
      parallel_workers: 8
    notify:
      channels: [phone_sre, dshb_lead, ops_manager]
      template: "L2-INDEX-MITIGATE-ACTIVE: {{index_expansion}}% at {{timestamp}}"
  failover:
    condition: "write_latency_p99 > 200ms"
    escalate_to: L3
```

### 5.5 L3: PROTECT — 自动降流保护

| 属性 | 值 |
|------|-----|
| **触发条件** | 索引膨胀率 ≥ **7.95%** 或 L2 限流导致 P99 延迟 > 500ms |
| **预期触发时间** | T0 + 24~48h (模型 C 极端场景) |
| **动作 1** | 流量自动降级: **75% → 60%** |
| **动作 2** | 索引写入 batch size: 100 → **10** |
| **动作 3** | 索引写入限流: max 500 ops/s |
| **动作 4** | 全量暂停非关键写入 |
| **动作 5** | 压缩频率 1x/h + batch size 10000 + parallel workers 16 |
| **动作 6** | **立即电话告警**: SRE oncall + 运维经理 + 技术 VP |
| **动作 7** | 创建 P0 级事件，启动故障响应流程 |
| **恢复条件** | 索引膨胀率 < 7.50% 且连续 6 小时稳定 |
| **恢复动作** | 逐步回切: 60% → 65% → 70% → 75% (每 2 小时一档) |
| **回退条件** | 降流后索引仍在增长 > 0.02%/h → 触发紧急回退到 50% |
| **预期效果** | 阻断膨胀增长，争取人工介入时间窗口 |
| **响应窗口** | ≤ 3 分钟 |
| **自动化等级** | 🔴 全自动 (不可人工覆盖，仅限运维经理 15 分钟后手动解除) |

**L3 降流配置**:
```yaml

  profile: L3_PROTECT
  trigger:
    condition: "index_expansion >= 7.95 OR write_latency_p99 > 500ms"
  actions:
    traffic_target: "60%"         # 从 75% 降至 60%
    traffic_reduction_mode: AUTO  # 自动，无需人工确认

      batch_size: 10
      max_ops_per_sec: 500

      frequency: "1h"
      batch_size: 10000
      parallel_workers: 16
    notify:
      channels: [phone_sre, phone_ops_manager, phone_tech_vp]
      template: "🚨 L3-INDEX-PROTECT-ACTIVE: index={{index_expansion}}% traffic={{traffic_percent}}% at {{timestamp}}"
    incident:
      severity: P0
      auto_create: true
      runbook: "DSHB-G1-INDEX-OVERFLOW"
  recovery:
    condition: "index_expansion < 7.50 AND stable_duration > 6h"

      - from: "60%" to: "65%" interval: "2h"
      - from: "65%" to: "70%" interval: "2h"
      - from: "70%" to: "75%" interval: "2h"
  failover:
    condition: "after_traffic_reduction_30m index_expansion_growth_rate > 0.02"

### 6.2 索引 Segment 合并策略

**Segment 生命周期管理**:

```

               ▲                  ▲                ▲              ▲
           实时写入          内存刷盘         压缩合并        段间合并
              (ms)          (1-5s)          (4-8s)         (10-30s)

**合并触发规则**:

| 触发条件 | 动作 | 频率 | 说明 |
|----------|------|------|------|

| Segment 总数 ≥ 100 | 触发中量合并 (merge 5 段→1 段) | 持续 | 控制 segment 增长 |
| 总 segment 数 ≥ 200 | 触发全量重建 (rebuild index) | 手动触发 | 最终手段 |
| Merge 积压 ≥ 20 段 | 优先压缩最老 segment | 自动 | 释放旧数据空间 |
| Segment 年龄 > 24h | 强制压缩 | 自动 | 避免旧 segment 膨胀 |

### 12.1 核心结论

| 结论项 | 内容 |

## 1. 概述

### 1.1 背景

本次作业是 **DSHB V86 RC2 G1** 组在 30 天稳定性维护期（Phase26，2026-10-27 至 2026-11-26）**首次** 在全流量在线环境下执行的索引 vacuum 操作。Phase25（2026-10-27 验收）已确认索引膨胀率稳定在 8.45%（峰值 8.72%），略高于 WARN 阈值 8.0%，但低于 CRITICAL 阈值 10.0%。

Phase26 维护期计划在第 15 天（2026-11-10）执行一次索引 vacuum 操作，目的是：

- 主动清理索引碎片，降低膨胀率至目标区间（< 7.0%）
- 延长索引寿命，将下次 vacuum 周期推迟至 Phase27 维护期
- 降低查询 P99 延迟，恢复至基线水平或更优
- 验证生产全流量环境下的 vacuum 操作风险可控

### 1.2 作业目标

| 目标项 | 目标值 | 实际值 | 状态 |
|--------|--------|--------|------|
| 索引膨胀率降低 | ≥ 2.0% | 2.70%（9.50% → 6.80%） | ✅ 达成 |
| 查询 P99 延迟改善 | ≥ 10% | 17.9%（168ms → 138ms） | ✅ 达成 |
| 业务中断事件 | 0 P0/P1 | 0 | ✅ 达成 |
| 快照备份完成 | 完成前校验通过 | 2.85TB / 15min | ✅ 达成 |
| 全作业窗口时长 | ≤ 2h30min | 1h45min | ✅ 达成 |

### 1.3 关键结论

- ✅ 本次 vacuum 是全流量环境下首次执行，整体运行平稳，无业务中断
- ✅ 膨胀率从 9.50% 降至 6.80%，低于 WARN 阈值 8.0%，恢复至 Phase25 基线 8.45% 以下

### 5.3 性能影响分析

#### 5.3.1 CPU 影响

| 指标 | 数值 |
|------|------|
| 基线 CPU | 88.2% |
| Vacuum 峰值 CPU | 92.5% |
| 增量 | +4.3% |
| 增量百分比 | +4.9% |
| 评估 | 🟡 可接受，距 95% 中止阈值仍有 2.5% 裕度 |

**分析**：CPU 峰值出现在 03:10–03:25（vacuum 处理 `dshb_idx_audit_log` 大表时），主要由索引重建的排序与 I/O 等待引起。由于限流至 8 workers，CPU 使用未超过安全裕度。

#### 5.3.2 I/O 影响

| 指标 | 数值 |
|------|------|
| 基线 I/O | 35% |
| Vacuum 峰值 I/O | 78% |
| 增量 | +43% |
| 评估 | 🟡 显著上升，但未达 95% 中止阈值 |

**分析**：I/O 峰值与 CPU 峰值同步，主要由 `dshb_idx_audit_log`（约 800GB 数据）的扫描与重排引起。存储层 SSD 阵列可承受该负载，未出现 IOPS 耗尽。

#### 5.3.3 查询延迟影响

| 指标 | 数值 |
|------|------|
| 基线 P99 | 168ms |
| Vacuum 期间峰值 P99 | 195ms |
| 劣化幅度 | +27ms (+16.1%) |
| 劣化持续时间 | 约 60min（02:45–04:00） |
| 业务影响 | 🟡 轻微，未触发业务告警 |

**分析**：查询 P99 劣化主要受 lock contention（锁竞争）与 buffer cache 预热不足影响。由于业务 QPS 在维护窗口期极低（1,250 vs 白天 8,600），实际受影响请求数约 75,000 次，占全日请求量 0.8%。

#### 5.3.4 锁竞争分析

| 锁类型 | 等待时长峰值 | 影响 |
|--------|-------------|------|
| AccessExclusiveLock | 单次 ≤ 30s（批量切换时） | 🟢 业务无感知 |
| ShareLock | 平均 12ms | 🟢 可接受 |
| RowExclusiveLock | 平均 8ms | 🟢 可接受 |

**结论**：pg_repack 在线重排机制有效避免了长时间持有排他锁，业务查询未出现阻塞。

## 9. 索引寿命延长评估

### 9.1 寿命延长原理

索引膨胀（index bloat）主要由以下操作产生：

1. **UPDATE 操作**：PostgreSQL 使用 MVCC 机制，UPDATE 不物理覆盖旧行，而是插入新版本行，旧版本行等待 vacuum 回收
2. **DELETE 操作**：删除的行不会立即物理移除，仅标记为 dead tuple
3. **索引重建**：B-tree 索引在频繁插入/删除后会形成碎片

**Vacuum 操作通过以下方式延长索引寿命**：

- 回收 dead tuple，释放页面
- 重排索引，降低碎片率
- 重建 B-tree，降低树高
- 更新统计信息，优化查询计划
